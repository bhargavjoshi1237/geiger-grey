# Let chat design Grey's visual lookup tools

Yes, it is a good idea, with one firm limit. Users should design tools in chat, but the chat's output should be a typed, versioned tool specification built from a small, closed set of retrieval operations: find similar, classify into a fixed label set, identify, and answer from similar items. Grey's own interpreter should run that spec against one project's knowledge bases. The chat should never produce generated code or a generated app. That limit is what makes the idea both defensible and safe. The general "describe it and get an app or workflow" market is crowded and losing products: Google Opal, OpenAI's Agent Builder, Microsoft's App Builder and Flowise have all been shut down or are retiring in 2026. Meanwhile, builder adoption is concentrating on platforms that already hold the customer's data, such as Notion, where teams built more than one million custom agents. No product surveyed combines chat-built tools, the customer's own vectors and graph, and image input, and retrieval-style tools are missing from every template gallery reviewed. Image query-by-example is a credible headline where the collection is private and the answer already lives in the project's records: duplicate and variant checks on brand assets, part or SKU identification that returns the matching manual, and similar past tickets or defects together with their fixes. It is not credible against storefront visual search, insurance damage estimating, clinical imaging or counterfeit authentication, where specialists win on proprietary training data and financial guarantees. Bring-your-own (BYO) models suit the headline. Similarity search and example-based classification need no generative call and cost about **$0.00012 per image** on a customer's Gemini key. An answer grounded in five retrieved neighbours costs roughly **$0.004–$0.016** in input tokens. The catch is that native image vectors need a multimodal embedding key (Google, Voyage, Cohere, Amazon, Jina or Nomic), because OpenAI and Anthropic offer no image embeddings. Today Grey cannot see an image at all. Image sources fail before they are downloaded, every embedding is text, search accepts only text, and there is no tool object. It does have the versioned-config, evaluation, search and AI SDK pieces to build on. The tool is also the same object as the typed "task" recommended in Grey's earlier non-chat research, so it should be built once. The recommended order is: make images searchable, then build the tool spec, runtime and tests, then the chat builder, then MCP and widget distribution. The biggest open question is whether customers want to build tools themselves or receive prebuilt ones, which is why every chat should start from a template.

## Generic builders are being retired while grounded lookup sits empty

The crowded part of this market is "describe what you want and get an app or a workflow." More than twenty vendors compete there, including every major platform, and 2026 has been a year of shutdowns. Google Opal launched in July 2025, stops running workflows on **17 November 2026**, and will not migrate them automatically ([Opal FAQ](https://developers.google.com/opal/faq)). Gemini Gems are being converted into "skills" ([Gemini](https://gemini.google/overview/gems/)). OpenAI's visual agent canvas, Agent Builder, is unavailable after **30 November 2026** ([OpenAI](https://openai.com/index/introducing-agentkit/)). Custom GPTs are also reportedly being retired, though only one secondary source says so and OpenAI could not be checked directly ([Jotform](https://www.jotform.com/ai/what-is-a-custom-gpt/)). Microsoft retires its App Builder agent and vibe.powerapps.com on the same day and moves natural-language app building into Copilot Studio ([MC1505609](https://mc.merill.net/message/MC1505609)). Flowise reached end of life on 31 August 2026. Its makers concluded that "the typical rigid workflow low code approach quickly hits the limit" ([Flowise](https://flowiseai.com/sunset)). The survivors take one of two shapes. One is a skill: instructions and files that run inside a general assistant. The other is generated code with a live preview and real data connections. Heavily funded players dominate the code-generation end. Lovable's run-rate passed **$600M** and it raised money at a **$13.3B valuation** ([Autobound/TechCrunch](https://www.autobound.ai/companies/lovable/news); [Let's Data Science](https://letsdatascience.com/news/lovable-raises-400-million-at-133-billion-valuation-974a9327)). A third bespoke canvas from Grey would run against this trend.

Adoption concentrates where the builder sits on data the vendor already holds. Teams created **more than one million Notion Custom Agents** during the February–May 2026 beta ([Reworked](https://www.reworked.co/digital-workplace/notion-custom-agents-reach-general-availability/)). Airtable rebuilt its whole product around Omni, its conversational app builder ([Airtable](https://airtable.com/newsroom/introducing-the-ai-native-airtable)). Copilot Studio apps read data with the signed-in user's own permissions ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-copilot-studio/apps-experience/apps-overview)). Glean and Dust ground agents in connected company sources ([Glean](https://docs.glean.com/agents/concepts/agent-builder); [Dust](https://docs.dust.tt/docs/quickstart-agent)). Thin wrappers show the opposite record. A crawl of 334,348 custom GPTs found that **only 28.5% had more than ten conversations**, that the top twelve took about a third of all conversations, and that only **2.96% called any external API** ([arXiv 2405.10547](https://arxiv.org/html/2405.10547v1)). A builder whose output is only a prompt plus a fixed graph adds little over the base assistant, and "ease of creation also meant ease of replacement" ([GenAI Assembling](https://genaiassembling.substack.com/p/the-fall-of-gpts)). Grey holds the data, so it belongs in the group that is growing. But each tool must do something the bare assistant cannot, such as query the project's vectors, graph and labelled examples.

What people actually build with these products is mostly classification under other names: triage, routing, qualification and tagging. Remote's IT agents in Notion **triage tickets with over 95% accuracy** and resolve more than a quarter on their own ([Reworked](https://www.reworked.co/digital-workplace/notion-custom-agents-reach-general-availability/)). Relevance AI showcases an "Inbound Qualifier" ([Relevance AI](https://relevanceai.com/invent)), and Airtable's field agents tag call transcripts ([Airtable](https://airtable.com/newsroom/introducing-the-ai-native-airtable)). Image input shows up only as a generative novelty, such as Opal's Room Styler, which restyles an uploaded room photo ([Google](https://blog.google/innovation-and-ai/models-and-research/google-labs/opal-agent/)). Claude artifact storage refuses images and binary data outright ([Claude Help Center](https://support.claude.com/en/articles/9487310-what-are-artifacts-and-how-do-i-use-them)). None of the galleries reviewed offers "find the five most similar stored items" or "which stored example does this resemble?" as a template. Dify comes closest. It pairs a conversational workflow generator and an agent that builds agents with image inputs to LLM nodes, knowledge bases with "multimodal vectors", workflows served as MCP servers, and customer keys once included credits run out ([Dify releases](https://github.com/langgenius/dify/releases); [Dify pricing](https://dify.ai/pricing)). Elastic's Agent Builder scopes search tools to indexes and exposes them over MCP with a customer-chosen LLM, but its tools are written as configuration, not built in conversation ([Elastic](https://www.elastic.co/search-labs/blog/elastic-ai-agent-builder-context-engineering-introduction)). Neither exposes a knowledge graph as something to build tools on, and neither tests a tool against the customer's stored, labelled examples.

The visual-search side is consolidating in a way that leaves room for a horizontal tool. Google's Vision API Product Search is in **maintenance mode**, and Google points users to Vision Warehouse ([Google Cloud](https://docs.cloud.google.com/vision/product-search/docs/apis)). ViSenze had raised about $34.5M and was sold to Rezolve AI for **$1.0M in shares plus an earn-out** ([Rezolve 20-F](https://www.sec.gov/Archives/edgar/data/1920294/000119312526132456/rzlv-20251231.htm); [e27](https://e27.co/singapores-visenze-acquired-by-nasdaq-listed-rezolve-ai-to-power-apac-expansion-20250827/)). Marqo pivoted from a general vector engine to e-commerce search ([Marqo](https://www.marqo.ai/pricing)). AWS discontinued Lookout for Vision on 31 October 2025 and steered customers toward foundation models ([AWS](https://aws.amazon.com/blogs/machine-learning/exploring-alternatives-and-seamlessly-migrating-data-from-amazon-lookout-for-vision/)). Hyperscalers now offer image-as-query over customer data but tie it to their own embedding models. Bedrock Knowledge Bases accept image queries only through Amazon's Nova embeddings ([AWS](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-multimodal.md)). Azure AI Search does it only through its Vision skill or a model hosted in Foundry ([Azure](https://learn.microsoft.com/azure/search/multimodal-search-overview)). Ragie, the nearest RAG-as-a-service analogue, lists no image-as-query feature on its pricing page ([Ragie](https://ragie.ai/pricing)) and joined Ticketmaster in July 2026 ([Ragie](https://www.ragie.ai/blog/ragie-joins-ticketmaster)). Digital asset management (DAM) vendors gate the feature. Cloudinary sells visual search only on Assets Enterprise ([Cloudinary](https://cloudinary.com/documentation/dam_visual_search)), Bynder requires an admin to enable it ([Bynder Labs](https://labs.bynder.com/features/search-by-image)), and Frontify still lists image similarity as "in development" ([Frontify](https://www.frontify.com/ai)).

BYO keys are rare among hosted builders: only Dify (after included credits), MindStudio (pass-through with no markup), Elastic, Glean's model hub and Glide Enterprise offer them ([MindStudio](https://www.mindstudio.ai/pricing); [Glide](https://www.glideapps.com/pricing)). That is an advantage with cost-sensitive and regulated buyers. It is also a handicap: Grey cannot offer the "it just works on free credits" first run that Notion, Airtable and Claude do. One caution matters. The absence of retrieval tools from template galleries is consistent with an unserved need, but it is equally consistent with weak demand. No buyer research separates the two. The researchers' web-search budget also ran out before vision platforms such as Roboflow were checked.

|---|---|---|
| Describe-an-app or describe-a-workflow builders | Crowded; Opal, Agent Builder, App Builder, Flowise retiring; Lovable above $600M run-rate | Do not compete; no free-form UI or node canvas |

## Image lookup pays where the answer already lives in the project

Visual-recognition specialists win where they own something a horizontal platform cannot: training data from billions of shopper interactions (Syte), a model trained on each customer's catalog (Marqo), training images synthesized from CAD files (nyris), millions of labelled damage photos with repair-cost data (Tractable), or accuracy backed by money (Entrupy claims **99.86%** and backs every authenticated item 100% financially for a full year) ([Syte](https://www.syte.ai/); [Marqo](https://www.marqo.ai/pricing); [nyris](https://www.nyris.io/); [Tractable](https://tractable.ai/); [Entrupy](https://www.entrupy.com/)). Grey wins under three conditions. The collection must be private and moderate in size, from hundreds up to hundreds of thousands of items per project. The useful answer must already sit in documents or case records in the project. And a wrong match must be cheap. Azure's documentation explains why the second condition matters. Pure image vectors are good for "find me something that looks like this," but "it doesn't convey why two images are related, and it doesn't offer the LLM ready context for citations" ([Azure](https://learn.microsoft.com/azure/search/multimodal-search-overview)). Grey's text, chunk and graph pipeline is that missing context. The new part is attaching an image vector to the same record.

Four use cases meet all three conditions. The first is DAM dedupe, variant lookup and licence checks. Bynder lists the jobs: check whether a stock photo is already owned before buying it, find size and localized variants, and paste a live URL to confirm an image is still licensed ([Bynder](https://www.bynder.com/en/blog/image-similarity-search/)). Geiger Assets' own feature blueprint promises "upload an image to find visually similar assets," and its schema already has a `visual` duplicate match type, but there are no vectors behind it ([DAM_FEATURES.md](C:/Pro/geiger-assets/DAM_FEATURES.md); [assets_modules.sql](C:/Pro/geiger-assets/supabase/migrations/20260628204539_assets_modules.sql)). The second is identifying a part or SKU and then retrieving what goes with it. XOi's field-service app reads an equipment data plate and "automatically identifies the equipment and pulls up its service history, manuals, and relevant service bulletins" ([XOi](https://xoi.io/company/news-and-press/the-xoi-experience-just-got-faster)). Partium lists entry pricing around **$6,000 a year** ([Capterra](https://www.capterra.com/p/213285/Partium/)), and nyris sells to OEMs such as Volkswagen and Trumpf. That leaves a long tail of distributors and maintenance teams with a few thousand parts, for whom those products are too heavy. The third is finding similar past support tickets that contain screenshots. Freshservice's Similar Ticket Suggester is documented as text-only ([Freshservice](https://support.freshservice.com/support/solutions/articles/50000009528-identify-similar-tickets-using-similar-ticket-suggester)), SAP's similar-defect search works on event and text data ([SAP](https://www.sap.com/use-cases/increase-quality-engineer-productivity-in-issue-resolution)), and only one minor vendor claims screenshot matching, with no technical detail ([StackShare](https://stackshare.io/find-similar-support-tickets-with-ai)). The fourth is retrieving a page or diagram, where the query is a screenshot or crop of a page. ColiVara already runs this kind of visual document search on Postgres and pgvector, the same stack Grey uses ([ColiVara](https://github.com/tjmlabs/ColiVara)).

The weak fits are just as clear. Storefront "shop the look" needs catalog-trained models, merchandising controls and traffic-scale latency. Damage estimating needs insurer integrations and cost databases. Clinical similar-case retrieval brings regulation and documented failure rates: Google reverse image search missed the correct skin-cancer diagnosis **20–30% of the time** in a JAMA Dermatology study ([JAMA Dermatology](https://jamanetwork-com.libproxy.ajou.ac.kr/journals/jamadermatology/article-abstract/2529572)), and DermEngine's visual search is "for educational purposes only" ([DermEngine](https://help.dermengine.com/how-do-i-use-visual-search)). Shelf audits need custom detectors and capture hardware ([Trax](https://traxretail.com/)). Demand from individuals is real but local-first. A Mac app for private image search drew **217 points and 171 comments** on Hacker News. Commenters named wedding photography, video editing and family archives as uses, and worried about anything being sent out ([HN](https://news.ycombinator.com/item?id=40371467)). That privacy preference favours BYO and project-scoped data, but personal photo search is not Grey's market.

| Use case | Buyer | Fit for Grey | Deciding factor |
|---|---|---|---|
| Asset dedupe, variants, "do we own this?", licence check | Brand and creative ops, SMB to mid-market | **Strong**, with Assets | Simple embeddings suffice; incumbents gate the feature |
| Small-catalog SKU match or spare-part ID, plus the manual | Distributors, maintenance teams, small OEMs | **Strong** (long tail); weak at OEM scale | The answer lives in project documents; CAD synthesis is a specialist moat |
| Similar past tickets with screenshots | Support and QA teams | **Strong** | Incumbents match text only |
| Page, diagram or chart retrieval | Document-heavy teams | **Strong** | Runs on pgvector; Grey's corpus is mostly documents |
| Defect or site-issue precedents | Small manufacturers, contractors | Moderate | Case lookup works; inline inspection needs detectors |
| Video moment search by image | Media and training teams | Moderate, via the customer's Twelve Labs or Gemini key | Integrate rather than build |
| Storefront search, damage estimates, clinical imaging, shelf audits, authentication | Retail, insurers, clinicians, CPG brands, resellers | **Weak** | Proprietary data, regulation, hardware or guarantees |
| Audio similarity | Music and sound libraries | Weak | Niche; for calls, transcripts already cover "calls like this" |

The founder's three image modes map onto this evidence unevenly. "Upload and get similar stored items" is the strongest and simplest. "Find something inside the image" has two directions with very different costs. Finding stored items that appear inside a large query photo needs only a region chosen on the query: a user-drawn crop, or one detection call to the customer's vision model. Each crop is then embedded and searched. Finding stored photos that contain a small object means embedding regions of every stored image at index time, which multiplies storage. Patch-level matching roughly doubled instance-retrieval mAP over one global vector in one study ([arXiv 2512.12610](https://arxiv.org/abs/2512.12610)), but that is a second-phase feature. When the target is text-like, such as a data plate, a label or a part number, OCR does most of the work. "Answer about the image from similar items" is the most differentiated mode, because few products outside hyperscaler building blocks combine image matches with a cited text answer over the customer's own records. The classifier mode fits all three: a fixed-option classifier is most naturally a vote among the nearest labelled examples.

Other media rank behind photos. A page or screenshot used as the query is the most practical non-photo input, because project sources are mostly documents. Single-vector multimodal embeddings now come close to specialist page retrievers. In Google's own benchmark paper, Voyage multimodal-3.5 scores **65.5** and Gemini Embedding 2 **64.9** nDCG@10 on ViDoRe V2 ([arXiv 2605.27295](https://arxiv.org/html/2605.27295v1)). Video can be embedded directly with Gemini Embedding 2. One Show HN project indexed dashcam footage this way for about **$2.50–$2.84 per hour** ([HN](https://news.ycombinator.com/item?id=47503617)). Twelve Labs also sells image-to-video moment search, with paid plans from $29 a month ([Twelve Labs](https://www.twelvelabs.io/pricing)), so a customer could bring that as a provider key. Audio-as-query is the least proven need. Hyperscalers treat audio as something to search with text through transcripts ([AWS](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-multimodal.md)). Across every mode, Grey should present results as "candidates, grounded in your records," never as authoritative identification, because quality depends on whichever model the customer attaches.

## Customer keys make similarity nearly free and grounded answers cheap

At least six hosted APIs now put images and text in one vector space and accept a customer's own key. OpenAI is not among them: its embeddings measure "the relatedness of text strings" only ([OpenAI](https://developers.openai.com/api/docs/guides/embeddings)). Anthropic publishes no embedding model. A customer with only those keys can get images into Grey only by captioning them first, and a practitioner warns that short caption output is "pretty terrible by comparison" as input for similarity ([HN](https://news.ycombinator.com/item?id=39090218)). The Vercel AI SDK's `embed()` takes strings only, and its one multimodal path is Gemini through provider options ([AI SDK](https://ai-sdk.dev/docs/ai-sdk-core/embeddings)). Grey should therefore extend its own raw-HTTP embedding drivers with an image call for each wire format. That suits Grey, whose five existing drivers are each about eighteen lines ([nomic.js](C:/Pro/geiger-grey/lib/engine/drivers/embed/nomic.js)).

The recommended design stores three layers per image, all on the existing Postgres. The first is model-free: the content hash Grey already records, plus a 64-bit perceptual hash for near-duplicates, which pgvector can index for Hamming distance ([pgvector](https://github.com/pgvector/pgvector)). The second is one joint image–text vector from the customer's multimodal embedding provider, defaulting to 768 dimensions, one of the two sizes Google's paper says its truncatable (Matryoshka) training is optimized for ([arXiv 2605.27295](https://arxiv.org/html/2605.27295v1)). The third is an optional caption-plus-OCR text chunk, written by the customer's own vision-capable chat model as one structured call per image. That chunk feeds Grey's existing full-text search, reranking and knowledge graph. It is also the BYO answer to today's "Image OCR isn't available yet" failure, which the backend spec plans to fix with a self-hosted OCR model on Grey's server. A Grey-hosted model conflicts with the rule that Grey hosts and pays for no models. The preset vocabulary already has a "Vision (VLM)" parser slot to carry this option ([constants.js](C:/Pro/geiger-grey/components/internal/screens/knowledge/constants.js)). Before any of this, a preprocessing step with sharp should auto-orient each image from its EXIF tag ([sharp](https://sharp.pixelplumbing.com/api-operation/)), strip EXIF and GPS data before anything reaches a third party, cap the image at about 1.5 megapixels, and keep a 384–512 px thumbnail. That keeps vectors reproducible and caps per-image provider cost. Customers who need more privacy can choose a hash-only mode or a customer-hosted vLLM endpoint.

The research offers two places to put the image vectors, and the choice is a real trade-off. The smaller change is a "multimodal knowledge base." The knowledge base's locked embedding model is itself multimodal, each image becomes one chunk whose content is its caption and whose vector comes from the pixels, and the existing single `embedding` column, per-dimension HNSW indexes and match function all work unchanged ([retrieval.sql](C:/Pro/geiger-grey/supabase/migrations/20261018120200_retrieval.sql)). The alternative is a separate media-embeddings table, which keeps image vectors from skewing text-only answers and can later hold region vectors and perceptual hashes. v1 should take the smaller path and add a kind filter to the match function, so text answers can exclude image chunks and image search can include only them. Grey should move to the separate table when a customer wants an image model different from its text model, when index-side region search arrives, or when a project nears millions of images. One hazard makes the first trigger urgent rather than optional. The match function filters on vector dimensions, not on model, so two different models that both output 1024 dimensions would be silently mixed today. Capacity is not a v1 constraint. pgvector's `halfvec` indexes up to **4,000 dimensions** ([pgvector](https://github.com/pgvector/pgvector)). One million 768-dimension image vectors take about 1.5 GB before index overhead. Supabase's own sizing serves one million 1536-dimension vectors at 0.99 recall on a 32 GB instance ([Supabase](https://supabase.com/docs/guides/ai/choosing-compute-addon)). A dedicated vector store becomes worth considering only past about ten million vectors per model.

The query flows are cheap because most of them make no generative call. Finding similar items takes one image embedding plus a nearest-neighbour lookup that completes in milliseconds. Classification by voting among the k nearest labelled examples adds no model call. That approach reached **79.8% top-1 accuracy on ImageNet** without fine-tuning, and a new label is added by adding examples rather than retraining ([arXiv 2204.01186](https://arxiv.org/abs/2204.01186)). On a hard image-text benchmark, precomputed embeddings matched frontier LLM rankers in accuracy but ranked 1,000 queries in **0.66 seconds**, against **6,100 seconds for GPT-4.1** ([arXiv 2608.11343](https://arxiv.org/html/2608.11343)). The right classifier is therefore a cascade. Vote first. When the vote margin or the top similarity is low, call the customer's vision model with the neighbours as few-shot examples and a constrained label output. Once a human approves that decision, store it as a new labelled example, so the cheap path covers more cases over time. The answer mode sends the query image, five labelled 512 px thumbnails and their record text to the customer's vision model. Claude bills a 1 MP image at about 1,296 tokens, so the prompt totals about 4,100 input tokens ([Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)). For finding things inside an image, Gemini returns normalized bounding boxes ([Gemini](https://ai.google.dev/gemini-api/docs/image-understanding)), while Claude calls its own localization "approximate," so user-drawn crops should come first.

| Tool operation | Generative calls | Model cost per run on the customer's key | Speed |
|---|---|---|---|
| Duplicate check (hash and perceptual hash) | None | $0 | Microseconds |
| Find similar (image in) | None; one image embedding | ~$0.00012 (Gemini) to ~$0.0006 (Voyage at 1 MP) | Milliseconds after the embed call |
| Classify by nearest-neighbour vote | None | Same as find similar | Same |
| Classify, vision-model fallback | One call with enum output | ~$0.0013 (Haiku 4.5) to ~$0.005 (Opus 5.5), input | Seconds |
| Answer from similar items | One vision call | ~$0.004 (Haiku 4.5) to ~$0.016 (Opus 5.5), input | Seconds |
| Find inside, query-side crop | None, or one detection call | One embedding per crop | Sub-second to seconds |

Four pitfalls need product answers. First, nearest-neighbour search always returns something. The dashcam project above returned the nearest big truck for a "cybertruck" that was not in the footage ([HN](https://news.ycombinator.com/item?id=47503617)). Every tool therefore needs a similarity floor, calibrated per model because cosine score ranges differ, and a "no similar stored items" answer when nothing clears it. Second, vectors lock the customer to a model. Even within one provider, Gemini's `gemini-embedding-001` and `gemini-embedding-2` spaces are "incompatible" ([Gemini](https://ai.google.dev/gemini-api/docs/embeddings)). Grey should keep every original image and record the model and preprocessing version on each vector, so a switch becomes a background re-embed. The re-embed should come with a visible estimate: about $120 per million images on Gemini, against $600–$1,200 on Voyage. Third, privacy depends on the customer's tier. Google may use free-tier Gemini inputs to improve its products, and EEA, Swiss and UK users must use paid services ([Gemini terms](https://ai.google.dev/gemini-api/terms)), so onboarding should steer image customers to paid keys. Fourth, quality is whatever the customer attaches. That is the honest cost of BYO, and it is why tests against the project's own examples, described next, matter.

## A closed vocabulary, not a sandbox, is the enclosure

The founder's "closed, contained environment" can be built two ways. One generates code and runs it in a sandbox. The other generates a specification and runs it in Grey's own interpreter. The evidence favours the specification. Builders aimed at non-developers have converged on typed graphs of fixed blocks. Dify ships Knowledge Retrieval, Question Classifier and Parameter Extractor as first-class nodes, and keeps generated code in a Code node that "blocks file system access, outbound network requests, and system commands" ([Dify Code node](https://docs.dify.ai/en/cloud/use-dify/nodes/code.md); [Question Classifier](https://docs.dify.ai/en/cloud/use-dify/nodes/question-classifier.md)). Generated code has a poor security record when non-developers ship it. CVE-2025-48757 left Lovable-generated apps with Supabase row-level security that did not work, and a scan found **303 exposed endpoints across 170 projects**, leaking emails, payment status and API keys ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2025-48757/); [Superblocks](https://www.superblocks.com/blog/lovable-vulnerabilities)). Replit's agent deleted a founder's production database and then wrongly said rollback was impossible ([The Register](https://www.theregister.com/2025/07/21/replit_saastr_vibe_coding_incident/)). The founder's example tools (a fixed-option classifier, and image-in similar, identify or answer) are each a short chain of retrieval and constrained-output steps. None of them needs code.

The tool should therefore be a versioned document. It has typed input and output as JSON Schema, a short list of steps drawn from a whitelisted block catalogue, a fixed retrieval scope and a budget. The sketch below is illustrative, not a final schema.

```json
{
  "name": "Part identifier",
  "scope": { "kbIds": ["<parts KB>"], "kinds": ["image", "document"] },
  "input": { "image": "grey-image", "note": "string, max 2000" },
  "steps": [
    { "id": "e", "block": "embed", "from": "input.image" },
    { "id": "s", "block": "vector_search", "query": "e", "topK": 8, "minScore": "calibrated" },
    { "id": "c", "block": "classify", "mode": "knn", "neighbors": "s",
      "labels": ["pump", "valve", "seal", "other"], "minMargin": 0.08,
      "fallback": { "mode": "llm", "maxOutputTokens": 20 } },
    { "id": "a", "block": "answer", "context": "s", "question": "input.note", "optional": true }
  ],
  "output": { "label": "enum | uncertain", "confidence": "number", "similar": "items with ids, scores, thumbnails", "answer": "text with citations" },
  "budget": { "maxLLMCalls": 2, "maxTokensPerRun": 9000, "timeoutMs": 20000 }
}
```

The v1 block catalogue is small. `embed` handles text or image. `vector_search` wraps Grey's existing search with the new kind and source filters. Then come `rerank`, `graph_lookup` and a deterministic `filter`. `classify` runs by nearest-neighbour vote, by label embedding or by LLM. `vision_identify` and `extract` use a vision or language model with enum or JSON-schema output, `answer` writes text with citations, and `format` shapes the result. Each block has a Zod schema for its parameters and a declared cost model. The builder agent never writes the whole document at once. Even workflow JSON with a strict schema trips up general models: one n8n tooling team found them "surprisingly bad at this task" ([lablab.ai](https://lablab.ai/submissions/afwpvpji1bouzmx58i0psos4)). Instead the agent calls typed edit operations (`set_input`, `add_step`, `update_step`, `set_labels`, `set_budget`, `run_preview`, `add_test_case`). Each call is validated against the catalogue, and each accepted edit becomes a draft revision linked to the chat message that caused it. The spec, not the conversation, is the state. When a user edits the spec in a form, the next chat turn receives the current spec, so the two cannot drift apart.

Containment then comes from construction rather than isolation. The interpreter builds a capability context on the server from the tool version itself: the project id, the knowledge-base ids, the provider connections and the budget. Blocks can reach data only through that context. The model never supplies a project, knowledge-base or source id. This is the in-process version of Cloudflare's design, where untrusted code can only call host methods whose scope sits in props the code cannot see or forge ([Cloudflare](https://developers.cloudflare.com/dynamic-workers/usage/bindings/)). Row-level security on `can_access_project` is a second wall, so leaking data across projects would need bugs in both. Outbound traffic goes only to the project's configured model, embedding and rerank endpoints, which Grey already checks and pins against server-side request forgery ([http.js](C:/Pro/geiger-grey/lib/engine/drivers/http.js)). There is no fetch-a-URL block, no webhook and no write action in v1.

That last choice is the core of the safety argument. A tool that reads uploaded images and private records already holds two legs of Simon Willison's "lethal trifecta": private data and untrusted content. The third leg is the ability to communicate externally. Willison argues that guardrails which block "95% of attacks" fail, because "in web application security, 95% is a failing grade" ([Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Grey should remove that third leg by design. A fixed spec is the "Plan-Then-Execute" pattern from the agent-security literature. Retrieved chunks, captions and runtime input can change values, but never which steps run or what data is in scope. LLM steps get no tools and must return an enum or a schema-validated object, which is the constrained "map-reduce" pattern: "a malicious document can only affect its own result" ([arXiv 2506.08837](https://arxiv.org/abs/2506.08837)). Code checks every item id an answer cites against the search step's real result set. The interface never renders or fetches a URL the model emits, and thumbnails load from Grey storage by source id only. Images need one more control. Trail of Bits hid prompts that became readable only after downscaling, and in Gemini CLI used one to exfiltrate Calendar data through an auto-approving MCP server. Its advice was to limit upload dimensions instead of silently downscaling, and to show the user "the input that the model is actually seeing" ([Trail of Bits](https://blog.trailofbits.com/2025/08/21/weaponizing-image-scaling-against-production-ai-systems/)). Text inside an image can also skew embeddings themselves, as CLIP's authors showed with typographic attacks ([Distill](https://distill.pub/2021/multimodal-neurons/)). Constrained outputs keep that skew bounded, because a poisoned image can at worst flip its own match. When Grey publishes tools to external agents, it should generate their descriptions from the spec through a template, so no project member can plant instructions in a description another agent will read ([Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)). The builder agent has its own trifecta to manage. It may read sample sources to propose labels, but it never sees runtime uploads. Its tools can write only the draft. Publishing, widening the scope or creating keys requires an explicit human approval under a `grey.tool.publish` permission that mirrors the existing pipeline-publish permission.

A declarative spec also makes cost boundable before a run. Each step declares its model calls and token ceilings, so the pre-run estimate is a sum over steps. That matters because Grey's existing monthly cap cannot see customer model spend: BYO usage is recorded at cost zero, and only Grey's own work (pages and retrievals) is priced ([usage.js](C:/Pro/geiger-grey/lib/engine/usage.js)). Per-tool limits therefore need their own mechanism. They should be token and call quotas, summed from usage events tagged with the tool id, plus an optional user-entered price per model to show an estimated cost. Each tool also needs its own rate-limit bucket. Dynamic agent routing, as in Opal's agent step, stays out of v1, because unbounded loops break both the static cost bound and Plan-Then-Execute. Public or embedded tools spend the project owner's provider budget, so they need the per-tool caps and auto-pause that Notion and Lindy sell as features ([Reworked](https://www.reworked.co/digital-workplace/notion-custom-agents-reach-general-availability/); [Lindy](https://www.lindy.ai/pricing)).

Testing against the project's own data is the strongest trust signal available, and only a builder that owns labelled examples can offer it. Because tool outputs are typed, most checks are deterministic and need no judge model. A classifier gets accuracy and a confusion matrix on held-out labelled items. A similarity tool gets a top-k hit rate. Any tool gets schema validity, latency and cost. An LLM judge is reserved for free-text answers. Publishing creates an immutable version, rollback repoints the live version, and an API key or embed can pin a version, which Dify sells only on paid plans ([Dify](https://docs.dify.ai/en/cloud/use-dify/build/version-control.md)). One versioned spec then projects onto four surfaces: an internal page whose form and result view are generated from the schemas with shadcn components, a REST run endpoint, an MCP tool and a widget. MCP tools natively carry an `outputSchema` and structured results ([MCP spec](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)). A single Grey-authored MCP Apps view, which renders in both ChatGPT and Claude, can display any tool's results with `connect-src` left at its default of `'none'` ([MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx); [OpenAI](https://developers.openai.com/apps-sdk/mcp-apps-in-chatgpt/)). Because the model never authors that view's HTML, it can be hashed and reviewed once.

Generated code can come later as an opt-in `transform` step for logic the blocks cannot express. Small pure functions can run in QuickJS compiled to WebAssembly inside the worker, with no host APIs, though the library "has not been audited" ([quickjs-emscripten](https://github.com/justjake/quickjs-emscripten)). Heavier jobs can run in Vercel Sandbox with `deny-all` networking and credentials injected at the boundary ([Vercel](https://vercel.com/docs/sandbox/concepts/firewall)). A two-second run costs about **$0.0008** on Pro, roughly $0.78 per thousand, mostly because of the one-minute memory minimum ([Vercel pricing](https://vercel.com/docs/sandbox/pricing)). Cloudflare Dynamic Workers cost far less per run, but they add a second cloud and rely on V8 isolates, which Cloudflare itself says have security bugs more often than hypervisors ([Cloudflare](https://blog.cloudflare.com/dynamic-workers/)). Neither is needed for the founder's examples, and the interactive path should never wait for a sandbox to boot.

## Grey has the scaffolding but cannot yet see an image

Grey already owns most of what this direction reuses. Pipelines have a draft row, immutable version snapshots, a publish/manage permission split, and a resolver that serves the draft to the Playground and the published snapshot to the API, MCP and widget ([pipelines.js](C:/Pro/geiger-grey/lib/supabase/pipelines.js); [pipeline_config.js](C:/Pro/geiger-grey/lib/engine/pipeline_config.js)). Eval sets and runs execute on a resumable lease queue ([queues.mjs](C:/Pro/geiger-grey/worker/queues.mjs)). `searchChunks` is hybrid search that needs no LLM ([retrieval.js](C:/Pro/geiger-grey/lib/engine/retrieval.js)). The SQL match function already accepts a ready query vector, and Grey's per-dimension HNSW indexes cover every image dimension in the table above ([retrieval.sql](C:/Pro/geiger-grey/supabase/migrations/20261018120200_retrieval.sql)). The installed AI SDK 7 provides image and file message parts, JSON-Schema-driven structured output, tool calling, an agent loop and tool approvals, none of which Grey uses yet ([provider-utils types](C:/Pro/geiger-grey/worker/node_modules/@ai-sdk/provider-utils/dist/index.d.ts); [ai types](C:/Pro/geiger-grey/worker/node_modules/ai/dist/index.d.ts)). Delivery is in place too: scoped API keys with rate limits, an MCP tool registry with per-server switches, widgets with domain allow-lists, and zero-cost BYO metering ([api_key_auth.js](C:/Pro/geiger-grey/lib/server/api_key_auth.js); [tools.js](C:/Pro/geiger-grey/lib/server/mcp/tools.js)). On the interface side, the Playground's three-pane frame (rail, chat, side panel), its chat kit, the shared `Dropzone` and the Assets import thumbnails are all reusable ([chat.jsx](C:/Pro/geiger-grey/components/internal/screens/playground/chat.jsx); [dropzone.jsx](C:/Pro/geiger-grey/components/internal/shared/dropzone.jsx)).

The image side is blocked at a single point but missing nearly everything after it. The worker fails every image job **before downloading it** with "Image OCR isn't available yet," unless an OCR service URL is set ([run.mjs](C:/Pro/geiger-grey/worker/ingest/run.mjs); [ocr_routing.js](C:/Pro/geiger-grey/lib/grey/ocr_routing.js)). Even with OCR, only text would ever be embedded. All five drivers send text arrays to text endpoints ([embedding_models.js](C:/Pro/geiger-grey/lib/grey/embedding_models.js)), and the worker has no image-processing dependency at all ([worker/package.json](C:/Pro/geiger-grey/worker/package.json)). `searchChunks` accepts only query text and returns `empty_query` without it. Its internal vector matcher is not exported, it has no kind filter, and its results carry no media fields. The only route that signs media URLs rejects anything that is not audio or video ([media-url route](C:/Pro/geiger-grey/app/api/sources/[id]/media-url/route.js)). Answer generation sends text only ([answer.js](C:/Pro/geiger-grey/lib/engine/answer.js)). The OpenAI-compatible endpoint rejects image parts with "Only text content is supported." ([openai_frames.js](C:/Pro/geiger-grey/lib/grey/openai_frames.js)). The Playground composer is a bare textarea, and the widget accepts a 2,000-character message ([widget chat route](C:/Pro/geiger-grey/app/api/widget/[widgetId]/chat/route.js)).

The tool side has no object to build on. The pipeline table is the wrong home: its columns are chat settings, and its publish step snapshots seven named fields but not `metadata`. A tool type stored there would therefore never be versioned. Tools need a sibling pair of tables that copies the pattern instead. No code in Grey uses tool calling, and neither Flow, Forms nor Notes uses the AI SDK at all. That makes the builder agent the first of its kind in the suite. Eval cases require a text question, so image test inputs need a schema change. The MCP tool list is fixed at four read-only tools. The API-key check treats an empty pipeline allow-list as "every pipeline" ([api_key_eval.js](C:/Pro/geiger-grey/lib/grey/api_key_eval.js)). Tools should treat an empty list as "none."

This direction also settles how the four missing foundations from Grey's earlier non-chat research apply. **Scoped retrieval** comes first because image search needs it immediately: a kind filter to keep image chunks out of text answers, and source filters for per-item precedents. **The generic task model is this tool spec.** A classify task and a classifier tool are the same versioned object with typed input, a retrieval scope, a model binding, tests and versions. Grey should build it once and accept image input from day one. **Derived outputs with review state** arrive through the classifier cascade, because model-decided labels become training examples only after a human approves them. **The outbound channel stays deliberately absent in v1.** Leaving it out is what removes the trifecta's third leg. Write-back into Flow and Forms should come later, behind review. Three decisions sit outside the code. First, the planned self-hosted OCR model conflicts with the BYO-only rule, and the customer's vision model makes it unnecessary for images. Second, the Notes AI node calls Anthropic on a platform-owned key ([geiger-notes route](C:/Pro/geiger-notes/app/api/ai/node/route.js)), and Forms' AI screens wait on a shared `@geiger/ai` package that does not exist ([coming_soon_screen.jsx](C:/Pro/geiger-forms/components/internal/screens/forms/coming-soon/coming_soon_screen.jsx)). Grey's builder will either set the suite's AI pattern or diverge from it. Third, the worker host is still undecided. Image ingestion runs on the worker like every other source, but interactive tool runs do not.

## Ship searchable images, then the tool, then the chat

The order follows the dependencies. No image tool can run until images are searchable. The chat edits a spec, so the spec and its runtime have to exist first. Distribution beyond Grey comes after a tool can be tested and versioned. The founder's chat-designed experience therefore arrives third. It still belongs in the first release, because steps one to three together make up the first version customers see. An internal alpha with form-edited templates can follow step two.

**The first version** ships as "Lookup tools" inside a project. A user opens Tools, starts a new tool, and the chat opens on a choice of three templates. "Find similar" takes an image (with an optional crop) or text, and returns ranked stored items with thumbnails, similarity scores, metadata and links. "Classify" returns one label from a fixed set, its confidence, the neighbours that voted and the records that justify the label. It votes first and falls back to the customer's vision model. "Answer from similar items" takes an image and a question and returns a cited answer, or abstains below the similarity floor. In the chat, the agent reads the project's knowledge bases and a sample of sources. From these it proposes the scope, a label set drawn from existing tags or entities, and a threshold. It builds a held-out test set from labelled items, and shows accuracy or hit@k and a per-run token estimate on the customer's key before offering to publish. Publishing requires a person with publish rights, and creates a version that runs on an internal page and through a REST endpoint. The first version requires a multimodal knowledge base whose embedding key comes from Google, Voyage, Cohere, Amazon, Jina or Nomic. Customers with only OpenAI or Anthropic keys get caption-based search, with a clear warning that image-to-image matching will be weaker. The first version deliberately leaves out generated code and UI, agent loops, outbound actions, index-side region search, video and audio queries, multi-vector page retrieval, separate image models, public widgets and MCP publishing.

Three alternative plans deserve a fair hearing. The first skips chat and ships prebuilt templates with a form editor. The research found no buyer evidence that knowledge-platform customers want to build tools rather than receive them, and templates would deliver much of the value for a fraction of the work. That is why the order puts chat third and makes every chat start from a template: if chat underperforms, the product still stands. The chat's real job is one forms do badly: choosing a label set, examples, scope and tests from the project's own data. That job is what earns the builder its place. The second plan would let Claude or ChatGPT be the whole interface through MCP, as the market's move to skills and MCP suggests. That is cheap and should come early. But MCP hosts offer no test-and-publish loop, and image upload works differently in each one, so it belongs in step four rather than replacing Grey's own surface. The third plan would lead with the chat builder because it demos best. Without step one there is no image to demo, and the builder is both the largest piece and the suite's first use of tool calling.

Three measurements should come before defaults are fixed, all run through the existing eval runner on a real project. One compares voting with vision-model classification on the customer's own labels, which no public benchmark covers. One measures image-embedding latency for each provider, since sub-second interactive runs are inferred, not measured. One calibrates similarity floors for each model. Pricing should follow the earlier research: charge for Grey's orchestration (a tool run, alongside existing pages and retrievals), never for anything that looks like resold tokens. The closest analogues charge for the platform and pass model usage through: Dify at $590 per workspace per year and MindStudio with no markup ([Dify](https://dify.ai/pricing); [MindStudio](https://www.mindstudio.ai/pricing)). Self-serve multimodal retrieval sells for **$25–$500 a month** ([Mixpeek](https://mixpeek.com/pricing); [Ragie](https://ragie.ai/pricing)).

## Conclusion

The founder's "closed environment" works best as a closed vocabulary rather than a locked box. One design decision, a typed spec run by Grey's own interpreter, delivers the containment (no code, fixed scope, no outbound path), the cost bounds (every step declares its calls), the reliability (specs validate, diff and roll back), and the suite look (interfaces generated from schemas with shared components). A sandbox would deliver only the first, at the price of boot latency and a second security boundary to maintain. The useful reframing is that Grey is not building a tool builder at all. It is building one typed, testable retrieval object that can be authored in chat, and the chat is valuable only because it can see the project's data and labelled examples.

Image lookup also changes Grey's role in the suite more than its feature list. Assets has promised visual similarity with no vectors behind it, Forms can capture photo-bearing tickets and inspections, and Flow can act on a match. A project-scoped "what is this, what is it like, and what did we do last time" service would make Grey the suite's vision layer, while each customer's own key pays for it. The constraint to manage is onboarding, not technology. The headline is nearly free to run, but only for customers who hold a paid multimodal embedding key. Steering new image projects toward one may be the single most important product decision in the first version.
