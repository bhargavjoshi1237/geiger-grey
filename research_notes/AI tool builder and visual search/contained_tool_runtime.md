# The "closed enclosure": an AI tool builder and contained runtime for Geiger Grey

Research date: 2026-10-21. Scope: the technical design of a chat-driven builder that designs a purpose-built tool (for example a fixed-option classifier, or "upload an image and find similar stored items, identify it, or answer from similar items") and runs it contained to one project's data, on Grey's stack (Next.js 16 on Vercel, Supabase Postgres with pgvector and RLS, a lease-based Node worker, bring-your-own model keys). The product market is covered by a separate researcher.

Method note: web search hit the session-wide budget partway through. The rest of the research used direct fetches of vendor docs, specs and engineering blogs. No Hacker News threads were read (see Gaps). Where a figure comes from a vendor's own marketing or from a secondary write-up, the entry says so.

Grey baseline (read from the repo, not the web), used throughout:

## 1. How should a generated tool be represented: declarative spec, sandboxed code, or UI only? Which do leading builders use, and why?

### Takeaway
The builders that ship to non-developers represent tools as a declarative graph of fixed, typed blocks. Google Opal, Dify, n8n and OpenAI's Agent Builder all do this, and Dify ships "Knowledge Retrieval", "Question Classifier" and "Parameter Extractor" as first-class nodes. Where they allow generated code, it is a contained escape-hatch node (Dify's sandboxed Code node) or a developer-oriented "code mode" over a narrow typed API (Cloudflare, Anthropic). UI-only generation (Claude AI-powered artifacts, MCP Apps, Apps SDK widgets) is a presentation layer, not a containment model. For Grey, the right shape is a JSON-Schema-typed declarative spec with an optional, tightly sandboxed code step, rendered by trusted components.

### Cited Findings
**(a) Declarative specs: step graphs and workflow JSON**
- Google Opal (Google Labs, US launch July 2025) turns a plain-language description into "a visual workflow comprising interconnected steps." Users can edit it in conversational or drag-and-drop mode and share it as a link that others run with their own Google accounts — [InfoQ](https://infoq.com/news/2025/07/google-opal-ai) (secondary coverage)
- On 24 Feb 2026 Opal added an "agent" step on Gemini 3 Flash that chooses tools and routes dynamically at runtime instead of following a fixed chain. It also added memory backed by Google Sheets and interactive steps that ask the user for input — [TechCrunch](https://www.techcrunch.com/2026/02/24/google-adds-a-way-to-create-automated-workflows-to-opal/); [Dataconomy](https://dataconomy.com/2026/02/25/googles-opal-now-builds-interactive-apps-that-ask-you-for-feedback/). Dynamic routing is exposed as an "@ Go to" tool — [KDnuggets](https://kdnuggets.com/how-im-using-google-opal-for-even-more-ai-automations) (secondary)
- Dify's node catalogue includes Knowledge Retrieval, Question Classifier, Parameter Extractor, Code (Python or JavaScript), Variable Assigner and Variable Aggregator nodes. These are the same building blocks the Grey brief names (vector search, classify, extract) — [Dify docs index](https://docs.dify.ai/_llms/en/cloud.txt); e.g. [Question Classifier](https://docs.dify.ai/en/cloud/use-dify/nodes/question-classifier.md), [Parameter Extractor](https://docs.dify.ai/en/cloud/use-dify/nodes/parameter-extractor.md), [Knowledge Retrieval](https://docs.dify.ai/en/cloud/use-dify/nodes/knowledge-retrieval.md)
- Dify apps export as a DSL. Exporting a *specific version's* DSL is a paid-plan feature — [Dify Version Control](https://docs.dify.ai/en/cloud/use-dify/build/version-control.md)
- n8n built its AI Workflow Builder on Claude "in just two months" — [Claude customer story: n8n](https://claude.com/customers/n8n). Third-party projects exist because "general purpose language models are surprisingly bad at this task since n8n workflow JSON has a strict schema". They research nodes, generate the JSON, validate it against the instance, then push — [FlowForge (lablab.ai)](https://lablab.ai/submissions/afwpvpji1bouzmx58i0psos4). A 2025 review found the builder not yet able to produce production-ready workflows without human intervention — [growwstacks review](https://growwstacks.com/blog/n8n-ai-workflow-builder-review/) (secondary)
- OpenAI Agent Builder (AgentKit, launched 6 Oct 2025) was a visual canvas with Preview, Evaluate, Code and Publish controls, inline evals and full versioning. **Deprecated:** an update dated 3 June 2026 says OpenAI is winding down Agent Builder and Evals, with access ending 30 Nov 2026. It points to the Agents SDK for code and Workspace Agents in ChatGPT — [OpenAI AgentKit page](https://openai.com/index/introducing-agentkit/) (read through search snippets; direct fetch returned 403). A third-party guide adds that existing evals go read-only on 31 Oct 2026, that the v1/prompts API also ends, and that ChatKit is not affected — [SpotDev](https://www.spotdev.co.uk/blog/agent-builder-wind-down-what-to-do) (secondary; it says it checked OpenAI's deprecations page on 8 Aug 2026)
- Tool contracts in the protocol layer are JSON Schema. An MCP tool has `name`, `title`, `description`, `inputSchema` (JSON Schema 2020-12 by default, "MUST be a valid JSON Schema object"), optional `outputSchema`, `annotations` and `execution.taskSupport`. If `outputSchema` is given, "Servers MUST provide structured results that conform to this schema" — [MCP spec 2025-11-25, Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)
- OpenAI Structured Outputs prevents "the model omitting a required key, or hallucinating an invalid enum value". It is "the evolution of JSON mode", and "only Structured Outputs ensure schema adherence". JSON mode is the older option — [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
- The AI SDK (the version in the current docs) takes Zod or JSON Schema `inputSchema`, validates tool calls (`InvalidToolInputError`) and supports per-tool `strict: true` where the provider supports it. Unsupported providers ignore it — [AI SDK: Tools and tool calling](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling)

**(b) Generated code, contained**
- Dify's Code node: "Code runs in an isolated sandbox that blocks file system access, outbound network requests, and system commands." Imports outside a pre-installed set fail. Outputs are capped (strings 400,000 chars, nesting depth 5) — [Dify Code node](https://docs.dify.ai/en/cloud/use-dify/nodes/code.md)
- Cloudflare "Code Mode": the model writes short TypeScript against a defined API instead of making sequential tool calls. Cloudflare reports "cut token usage by 81%" when an MCP server is turned into a TypeScript API. It also says its own MCP server exposes its full API through two tools in "under 1,000 tokens". It argues that "narrow TypeScript wrappers are easier to secure than filtering HTTP traffic" — [Cloudflare blog: Dynamic Workers (2026-03-24)](https://blog.cloudflare.com/dynamic-workers/)
- Anthropic's "Code execution with MCP" (4 Nov 2025) presents MCP servers as code APIs. It reports token use falling "from 150,000 tokens to 2,000 tokens" (98.7%). Intermediate data stays in the execution environment ("the agent only sees what you explicitly log or return"). The stated cost is that it "requires a secure execution environment with appropriate sandboxing", plus resource limits and monitoring — [Anthropic Engineering](https://www.anthropic.com/engineering/code-execution-with-mcp)

**(c) Generated UI only**
- Claude "AI-powered artifacts" (25 Jul 2025) are generated apps that call Claude through "a text-based completion API". The point that matters most for Grey: "Their API usage counts against *their* subscription, not yours". At launch there were "No external API calls (yet)" and "No persistent storage" — [Claude blog](https://claude.com/blog/claude-powered-artifacts)
- MCP Apps and the OpenAI Apps SDK render a server-supplied HTML UI in a sandboxed iframe. The tool logic stays on the MCP server (see section 3) — [MCP Apps spec 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)
- AI SDK generative UI: "Generative UI is the process of connecting the results of a tool call to a React component". The model emits structured tool calls, and the app renders its own predefined components (typed `tool-${toolName}` parts with `input-available | output-available | output-error` states). The model does not generate the markup — [AI SDK generative UI](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces)

### Inferences
- Builders aimed at non-developers (Opal, Dify, n8n, the former Agent Builder) all converge on a typed step graph. A spec can be validated before it runs, diffed, versioned, rendered as a form, and explained back to the user. Generated code can't easily be any of these. The n8n evidence, that LLMs struggle with strict workflow JSON, argues for the builder to edit the spec through small typed patch operations (add step, set labels, set filter) validated by Zod. One-shot generation of the whole document is weaker.
- Grey's brief already names a small closed set of blocks (embed, vector search, filter, classify, extract, LLM answer). Dify's Question Classifier and Parameter Extractor nodes show that a fixed-option classifier and a field extractor are well served by parameterised blocks. Neither needs generated code.
- Code is best kept as an opt-in "transform" step for things the blocks can't express, such as custom scoring or reshaping JSON. That mirrors Dify's Code node: no network, no filesystem, typed inputs and outputs.
- "UI only" (artifact-style) is unsuitable as the containment model for Grey. The UI would need project-data access, which pushes data access into the browser. The useful lesson from Claude artifacts is the cost model: usage billed to the person running the app. That maps directly onto Grey's BYO-key model.
- Deprecation to note: OpenAI Agent Builder and its hosted Evals end 30 Nov 2026, so neither is a dependency option. JSON mode is superseded by Structured Outputs.

### Gaps
- Microsoft Copilot Studio topics and Zapier's AI builders were not researched (search budget exhausted). No first-party source was read on whether n8n's built-in builder emits JSON directly or patches the canvas.
- Dify's DSL schema itself (YAML structure, versioning field) was not read. The DSL docs page could not be located through the docs index.
- Opal's internal representation (whether it is a serialisable graph format and whether it can be exported) was not confirmed from a Google primary source.

## 2. How is a tool contained to one project's data (capabilities, scoped tokens, RLS, egress, limits), and how do Vercel Sandbox, E2B, Cloudflare and others isolate code, at what cost and latency (2026)?

### Takeaway
Containment comes in two layers. The first is *data reach*: capability objects or scoped tokens, so code can only call project-scoped operations whose scope the host sets. The second is *compute plus network isolation*: an isolate or microVM with deny-by-default egress and credentials injected at the boundary. Cloudflare Dynamic Workers is the cleanest capability model (unforgeable RPC stubs with host-held `ctx.props`, `globalOutbound: null`). Vercel Sandbox gives Firecracker microVMs with a policy firewall and credential brokering, on Grey's existing vendor. For a declarative spec interpreted by Grey's own code, no sandbox is needed at all: containment is the interpreter plus RLS plus fixed scope.

### Cited Findings
**Capability-based data access**
- Cloudflare Dynamic Workers get only what the loader passes in `env`. The loader exports a `WorkerEntrypoint` class whose methods are the only operations the dynamic code can call, and `ctx.exports.X({ props })` makes a stub. "Stubs have no global identifier and cannot be forged". Props are visible only to the loader, and each call is an RPC back to the loader, which can inspect, transform or reject it. In the tenant example `MyStorage.get(key)` reads `${this.ctx.props.prefix}:${key}`, so a tenant can only touch its own prefix — [Cloudflare: Dynamic Workers bindings](https://developers.cloudflare.com/dynamic-workers/usage/bindings/)
- Egress: `globalOutbound: null` makes "Any `fetch()` or `connect()` call from the dynamic Worker throws an exception". Alternatively `globalOutbound: ctx.exports.HttpGateway({ props: { tenantId } })` routes all outbound requests through a gateway that can block them or inject `Authorization`/`X-Tenant-Id` headers the dynamic code never sees — [Cloudflare: Egress control](https://developers.cloudflare.com/dynamic-workers/usage/egress-control/)
- quickjs-emscripten (QuickJS compiled to WASM, usable in-process in Node): "By default, no host functionality is exposed to code running inside QuickJS". Host APIs are added explicitly (`newFunction`, `setProp`). Limits come from `runtime.setMemoryLimit`, `setMaxStackSize`, per-eval `memoryLimitBytes`, and `shouldInterruptAfterDeadline` / `setInterruptHandler` for time. Caveats: "has not been audited", pre-1.0, manual handle disposal, and an asyncify build that is about 2x larger, slower, and allows only one suspended async call at a time — [quickjs-emscripten README](https://github.com/justjake/quickjs-emscripten)
- OWASP LLM01 mitigation 4, "Enforce least privilege": give the application its own API tokens, "handle extended functions in code rather than through the model", and limit model access to what it strictly needs — [OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)
- MCP guidance on scopes: start from a minimal scope set and elevate incrementally. Common mistakes include "Using wildcard or omnibus scopes (`*`, `all`, `full-access`)". Token passthrough is forbidden: "MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server" — [MCP Security Best Practices 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)
- Grey already has API keys with `scopes[]` limited to `retrieve | chat | mcp` (`ALLOWED_SCOPES`), `pipeline_ids[]`, `rate_limit_per_min` (1–10000, default 60) and expiry. All tables are RLS-scoped by `grey.can_access_project(project_id)` — [grey_current_capabilities.md](C:/Pro/geiger-grey/research_notes/Knowledge%20base%20uses%20beyond%20chat/grey_current_capabilities.md) (`app/api/api-keys/route.js`, `20261010120000_grey_core.sql`)

**Vercel Sandbox (Firecracker microVM)**
- "each sandbox runs in its own Firecracker microVM with a dedicated kernel". It has kernel-level process isolation, its own network namespace, "Strict CPU, memory, and disk limits" and automatic timeouts. Startup is described as "Milliseconds (Firecracker optimized for fast boot)" (vendor claim, no figure), and resuming from a snapshot is faster than a fresh create. Sandboxes are persistent by default (filesystem snapshotted on stop). "Runtimes" are deprecated in favour of images — [Vercel: Understanding Sandboxes](https://vercel.com/docs/sandbox/concepts); [Vercel Sandbox pricing](https://vercel.com/docs/sandbox/pricing)
- Firewall modes: `allow-all` (default), `deny-all` ("Denies all outbound network access, including DNS") and user-defined allowlists (domains with wildcard labels, CIDRs, denied CIDRs). Policies can be updated live, for example install packages, then `sandbox.update({ networkPolicy: 'deny-all' })`, then run untrusted code. **Credentials brokering** (`transform` headers) injects secrets at the boundary so "The secrets never enter the sandbox". `forwardURL` proxies requests to your own endpoint with a `vercel-sandbox-oidc-token`. Caveats: SNI-only matching allows domain fronting, matchers never block, and `subnets.allow` leaves DNS unrestricted — [Vercel: Sandbox firewall](https://vercel.com/docs/sandbox/concepts/firewall)
- "Isolation without egress control contains the process, not its consequences." Recommended pattern: deny by default, temporary connectivity, credentials injected at the boundary, your own proxy for payload inspection — [Vercel blog, 11 Aug 2026](https://vercel.com/blog/a-sandbox-without-a-network-boundary-is-only-half-a-sandbox)
- Pricing (Pro, iad1): Active CPU $0.128/h (I/O wait not billed); provisioned memory $0.0212/GB-h, billed in 1-minute minimum increments (2 GB per vCPU); creations $0.60 per 1M; snapshot storage $0.08/GB-month. Limits: 10,000 concurrent sandboxes, 24 h max session, default timeout 5 min, max 8 vCPU / 16 GB on Pro. Hobby: 5 CPU-h, 420 GB-h, 5,000 creations/month, 10 concurrent, 45 min. Vercel's own example "Quick test, 2 min, 1 vCPU, 2 GB" costs $0.0018 — [Vercel Sandbox pricing](https://vercel.com/docs/sandbox/pricing)

**E2B**
- Usage pricing is $0.000014 per vCPU-second and $0.0000045 per GiB-second. Sizes run from 1–8 vCPU and 1–8 GiB (default 2 vCPU / 4 GiB), CPU only. Hobby is $0 with a one-time $100 credit, 20 concurrent and 1 h sessions. Pro is $150/month plus usage, 100 concurrent, 24 h sessions (add-ons up to 1,100 concurrent for $1,150/month). Enterprise has a $3,000/month minimum — [E2B pricing](https://e2b.dev/pricing)
- Egress: `allowInternetAccess: false`, or `network: { denyOut, allowOut }` with IPs, CIDRs and domains (allow beats deny, domains only in allow lists, HTTP Host / TLS SNI filtering, no QUIC). `updateNetwork` changes rules live. Per-host header-injection `network.rules` is in public beta. Caveat: a denied TCP connect "can appear to succeed" — [E2B: Internet access](https://docs.e2b.dev/sandbox/internet-access)
- Startup "~150ms" is repeated widely but only by third parties. Morph lists "<200ms". No official E2B figure was found — [SoftwareSeni](https://www.softwareseni.com/e2b-daytona-modal-and-sprites-dev-choosing-the-right-ai-agent-sandbox-platform); [Morph comparison](https://www.morphllm.com/comparisons/e2b-vs-daytona)

**Cloudflare Dynamic Workers (V8 isolates)**
- Open beta since 24 Mar 2026 on the Workers Paid plan — [Cloudflare changelog](https://developers.cloudflare.com/changelog/post/2026-03-24-dynamic-workers-open-beta/). No GA announcement was found; the docs page was last updated 12 Oct 2026 — [Dynamic Workers overview](https://developers.cloudflare.com/dynamic-workers/)
- "An isolate takes a few milliseconds to start and uses a few megabytes of memory", against containers taking "hundreds of milliseconds to boot and hundreds of megabytes". That is "around 100x faster and 10x-100x more memory efficient". Caveat in the same post: "security bugs in V8 are more common than security bugs in typical hypervisors". Mitigations listed: V8 patches within hours, a second-layer sandbox with risk-based tenant cordoning, MPK hardware extensions, Spectre research, and malicious-code scanning. Helpers: `@cloudflare/codemode` (`DynamicWorkerExecutor`), `@cloudflare/worker-bundler`, `@cloudflare/shell` — [Cloudflare blog](https://blog.cloudflare.com/dynamic-workers/)
- Pricing: 1,000 unique Dynamic Workers/month included, then $0.002 per Dynamic Worker per day. A Worker is unique by ID + code: the same code and ID invoked many times counts once, while `.load(code)` without an ID counts once *per invocation*. Requests are $0.30/M after 10M; CPU is $0.02 per million CPU-ms after 30M, and isolate start-up is billed as CPU — [Dynamic Workers pricing](https://developers.cloudflare.com/dynamic-workers/pricing/). The blog says the $0.002 fee is waived during beta — [Cloudflare blog](https://blog.cloudflare.com/dynamic-workers/)

**Others**
- Modal Sandboxes bill at "non-preemptible rates of 3x list price": $0.00003942 per physical-core-second (1 core = 2 vCPU) and $0.00000667 per GiB-second. Plans: Starter $0 + $30/month credit, Team $250/month + $100 credit. Modal "spins containers up and down in 1-2 seconds" — [Modal pricing](https://modal.com/pricing)
- Deno Sandbox (Deno Deploy cloud) gives lightweight Linux microVMs for LLM-generated code. Secrets never enter the environment: code sees a placeholder, and the real key is substituted only on outbound requests to approved hosts. Egress policies are strict — [Deno blog: Introducing Deno Sandbox](https://deno.com/blog/introducing-deno-sandbox); [Deno Sandbox docs](https://docs.deno.com/sandbox/) (vendor claims; read via search summaries)
- OWASP LLM10 (Unbounded Consumption) mitigations: input size limits, rate limiting and quotas, dynamic resource allocation, timeouts and throttling, limits on queued and total actions, monitoring, graceful degradation, and sandboxing that restricts network, internal service and API access. It defines "Denial of Wallet" but gives no mitigation specific to it — [OWASP LLM10:2025](https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/)

### Inferences
- **Per-run cost, worked from the cited rates** (my arithmetic, short tool runs):
  - Vercel Sandbox, 1 vCPU / 2 GB, about 2 s of active CPU, stopped immediately. The 1-minute memory minimum dominates: 2 GB × 1/60 h × $0.0212 ≈ $0.00071, plus CPU 2/3600 h × $0.128 ≈ $0.00007, plus creation ≈ $0.0000006. That is ≈ $0.0008 per run, or **≈ $0.78 per 1,000 runs**, before Function time and network.
  - E2B, 2 vCPU / 4 GiB for 10 s: 2×10×$0.000014 + 4×10×$0.0000045 ≈ **$0.00046 per run** ($0.46 per 1,000) plus $150/month Pro. Whether E2B applies a minimum billing increment is not stated.
  - Modal Sandbox, 1 core / 4 GiB for 10 s: ≈ $0.00039 + $0.00027 ≈ **$0.00066 per run**.
  - Cloudflare Dynamic Worker with a stable ID per tool version, 50 CPU-ms: ≈ $0.000001 CPU + $0.0000003 request per run, plus $0.002 per tool version per day. 1,000 runs a day of one tool comes to **≈ $0.003/day**. Using `.load()` without an ID would cost $0.002 *per run* ($2 per 1,000), so tool-version-hash IDs matter.
  - An in-process QuickJS step or Grey's own interpreter adds no vendor fee beyond Vercel Function or worker CPU.
- **Latency order** (vendor and secondary figures): V8 isolates and in-process WASM take a few ms; Firecracker microVMs are claimed at "milliseconds" (Vercel) and ~150 ms (E2B, third-party); containers take 1–2 s (Modal's own claim). For an interactive "upload an image, get similar items" tool, a microVM create per run adds avoidable latency. A declarative interpreter has none.
- For a declarative spec, Grey's runtime *is* the capability layer. Each block calls an existing engine function (`searchChunks`, `embedTexts`, `kg_expand`) through a context object the server builds from the tool's own `project_id` and `kb_ids`. The model never supplies those values. This is the Cloudflare `ctx.props` pattern implemented in-process. RLS (`can_access_project`) is the second wall. Cross-project leakage would require bugs in both.
- If and when Grey runs generated code, the code must not get a Supabase key or a provider key. On Vercel Sandbox it should run under `deny-all` and receive data through files or stdin and return JSON. Model calls from code should go through a Grey proxy via `forwardURL`, or not happen at all. On Cloudflare the equivalent is `globalOutbound: null` plus a `GreyProject` `WorkerEntrypoint` stub whose props hold project id and tool id.
- Vercel Sandbox fits Grey's existing vendor, billing and OIDC. Dynamic Workers is cheaper and faster per run, but it adds a second cloud and runs on V8 isolates, which Cloudflare itself says are a weaker boundary than hypervisors.

### Gaps
- No measured cold-start numbers for Vercel Sandbox `Sandbox.create()` (only "milliseconds"), Daytona, or Deno Sandbox. No official E2B startup figure was found.
- Daytona, Pyodide and Cloudflare Workers for Platforms were not researched (search budget). Dynamic Workers is described by Cloudflare as "the lowest-level primitive for spinning up a Worker".
- No source was read on Dynamic Workers' configurable CPU and memory limits (the Limits subpage was not fetched).
- Supabase-specific patterns for minting per-tool JWTs with custom claims for RLS were not researched in this session.

## 3. How do Claude Artifacts, MCP Apps, the OpenAI Apps SDK and AI SDK generative UI render tool UIs safely (iframe sandbox, CSP, postMessage), and what is the state of MCP Apps in 2026?

### Takeaway
MCP Apps (SEP-1865, stable spec 2026-01-26) is now the cross-host standard. Both ChatGPT and Claude implement it, and OpenAI's `window.openai` / `openai/*` keys survive as compatibility aliases. Its safety model has five parts: mandatory sandboxed iframes, a separate-origin sandbox proxy on web hosts, CSP derived from declared `connectDomains`/`resourceDomains`/`frameDomains` (default `connect-src 'none'`), JSON-RPC over `postMessage`, and tool visibility flags (`model` / `app`). Inside Grey's own app, AI SDK-style generative UI (trusted components fed typed tool output) is safer than rendering model-generated HTML.

### Cited Findings
- Spec status: stable `2026-01-26`, plus a `draft` in progress. The ext-apps 2.x SDK requires `@modelcontextprotocol/client` ^2.0.0 and Node 20+, and the wire protocol is unchanged between 1.x and 2.x. Listed hosts: ChatGPT, Claude, VS Code, Goose, Postman, MCPJam, mcp-use Inspector and Alpic Playground ("Host support varies"). MCP-UI's client SDK is described as a "fully-featured MCP Apps framework" — [ext-apps README](https://github.com/modelcontextprotocol/ext-apps)
- UI resources use the `ui://` scheme, and `mimeType: "text/html;profile=mcp-app"` is mandatory. "All View content must render in sandboxed iframes". Web hosts must use a **sandbox proxy** on a different origin (`allow-scripts allow-same-origin`) that receives the HTML via `ui/notifications/sandbox-resource-ready` (`html`, `sandbox`, `csp`, `permissions`) and loads the View with CSP derived from metadata — [MCP Apps spec 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)
- CSP metadata `_meta.ui.csp`: `connectDomains` → `connect-src` (default `'none'`), `resourceDomains` → img/script/style/font/media-src, `frameDomains` → `frame-src` (default `'none'`), `baseUriDomains` → `base-uri`. Hosts "MUST NOT allow undeclared domains" and "SHOULD log CSP configurations". Permissions (`camera`, `microphone`, `geolocation`, `clipboardWrite`) map to the iframe `allow` attribute, which hosts "MAY honor". One inconsistency: the default says `connect-src 'none'`, but an example in the Security section uses `'self'` — same spec
- Bridge methods: View→Host `ui/initialize`, `tools/call`, `resources/read`, `ui/open-link`, `ui/message`, `ui/request-display-mode`, `ui/update-model-context`. Host→View `ui/notifications/tool-input` / `tool-input-partial` / `tool-result` / `tool-cancelled` / `host-context-changed`, `ui/resource-teardown`. Visibility `_meta.ui.visibility` defaults to `["model","app"]`. Hosts "MUST NOT" list tools lacking `"model"` to the agent and "MUST reject" app `tools/call` for tools lacking `"app"`. Cross-server calls to app-only tools are blocked. Per-call consent for UI-initiated `tools/call` is *not* mandated (hosts "MAY"). The stated threat model covers malicious HTML, sandbox escape, unauthorized tool execution, exfiltration and phishing, and hosts should hash or sign predeclared HTML — same spec
- ChatGPT "implements the open MCP Apps standard". Tools declare `_meta.ui.resourceUri`, resources are `text/html;profile=mcp-app`, and the bridge is "JSON-RPC over `postMessage`" with `ui/*` methods. `openai/outputTemplate` and `window.openai.*` are compatibility aliases. "New UI should use the shared fields and bridge methods". `window.openai` remains only for extensions such as checkout, modals, files and `widgetState`. "Treat the resource URI as a cache key" and publish a new `ui://` URI after breaking changes. "Nested frames are blocked by default". "The plugin review process checks the declared policy against the UI behavior" — [OpenAI: MCP Apps in ChatGPT](https://developers.openai.com/apps-sdk/mcp-apps-in-chatgpt/)
- Apps SDK security guidance: widgets run "inside an isolated iframe with a strict Content Security Policy" and cannot use dialog or clipboard APIs. `connectDomains`/`resourceDomains` don't restrict requests made inside an embedded page. Keep secrets and tokens out of component props. "Assume prompt injection and malicious inputs will reach your server". Require human confirmation for irreversible operations, and enforce OAuth scopes on every tool call — [OpenAI Apps SDK: Security & Privacy](https://developers.openai.com/apps-sdk/guides/security-privacy)
- Claude renders MCP Apps inline after a permission prompt ("Allow" / "Always allow"). Register with `registerAppTool()` / `registerAppResource()` so one codebase emits each host's metadata. Claude's `ui.domain` is the first 32 hex chars of SHA-256(server URL) + `.claudemcpcontent.com`. A migration guide from the OpenAI Apps SDK is provided — [Claude docs: Get started with MCP Apps](https://claude.com/docs/connectors/building/mcp-apps/getting-started)
- AI SDK generative UI renders app-owned React components from typed tool output. Model output stays data, not code — [AI SDK generative UI](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces)
- Claude AI-powered artifacts are shareable by link with "no deployment process needed". The launch post gives no sandbox details — [Claude blog](https://claude.com/blog/claude-powered-artifacts)

### Inferences
- For a Grey tool, the UI can be *derived* from the spec rather than generated as code. Use a form from `inputSchema` (text field, enum select, image dropzone) and a result renderer from `outputSchema` (label chip with confidence, ranked list of similar items with thumbnails and citations, answer with citations). Both are built from Grey's shadcn components. That is the AI SDK generative-UI approach, and it removes the "malicious HTML" threat class inside Grey.
- For external hosts, Grey can ship **one** generic, pre-built MCP Apps resource (for example `ui://grey/tool-runner@<hash>`) that renders any tool's `structuredContent` by its output schema. It would declare no `connectDomains`, with images passed as data URIs or signed URLs listed in `resourceDomains`. The model never authors the HTML, the resource can be hashed and reviewed once, and the same View works in ChatGPT and Claude.
- If Grey ever lets the model generate custom widget HTML, it should follow the MCP Apps rules in its own app: a separate-origin sandbox iframe, `connect-src 'none'`, and a postMessage bridge whose only callable method is "run this tool version". That is a later phase, not v1.

## 4. How do builders let users test a tool before publishing, version it and roll it back, and keep the conversation and the tool spec in sync?

### Takeaway
The common pattern is draft → test → publish an immutable version → roll back by restoring or repointing. Dify has a current draft, a "latest" live version and named previous versions with release notes, plus single-node step runs, run history and a variable inspector. OpenAI's Agent Builder had Preview, inline evals and versioning but is being shut down. ChatGPT asks for UI versioning by immutable resource URIs. Grey already has the same draft/live plus immutable-version plus eval-set machinery for pipelines, and it can be reused for tools. No vendor documents how it keeps chat and spec in sync. The safe design treats the spec as the source of truth and has every chat edit produce a validated, diffable draft revision.

### Cited Findings
- Dify version control (Chatflow and Workflow apps only): "Current Draft: Your working version… Not live for users"; "Latest Version: The live version users see"; previous versions are kept. Publish turns the draft into the latest version and opens a fresh draft. Versions can be named and given release notes. Loading an old version "replaces your current draft completely", and the docs suggest restoring as the quick rollback. Restore, per-version DSL export and running a specific published version via API need a paid plan. On the free Sandbox plan apps always run the latest published version — [Dify Version Control](https://docs.dify.ai/en/cloud/use-dify/build/version-control.md)
- Dify debugging surfaces: Single Node (step run), Run History, Variable Inspector, Error Types, and predefined error-handling logic. The Code node supports retries (up to 10, interval ≤ 5000 ms) and fallback paths — [Dify docs index](https://docs.dify.ai/_llms/en/cloud.txt); [step run](https://docs.dify.ai/en/cloud/use-dify/debug/step-run.md); [run history](https://docs.dify.ai/en/cloud/use-dify/debug/history-and-logs.md); [variable inspector](https://docs.dify.ai/en/cloud/use-dify/debug/variable-inspect.md); [Code node](https://docs.dify.ai/en/cloud/use-dify/nodes/code.md)
- Dify publishing "replaces your live app with the current configuration", and embeds "automatically reflect all changes". Published surfaces follow the latest version unless pinned (pinning is paid) — [Dify Publish](https://docs.dify.ai/en/cloud/use-dify/publish/README.md)
- OpenAI Agent Builder had Preview, Evaluate, Code and Publish controls, preview runs, inline eval configuration and full versioning. It is being wound down, with access ending 30 Nov 2026 — [OpenAI AgentKit](https://openai.com/index/introducing-agentkit/) (via search snippets); [SpotDev](https://www.spotdev.co.uk/blog/agent-builder-wind-down-what-to-do)
- ChatGPT: "Treat the resource URI as a cache key". Publish a new `ui://` URI after breaking HTML, JS or CSS changes — [OpenAI: MCP Apps in ChatGPT](https://developers.openai.com/apps-sdk/mcp-apps-in-chatgpt/)
- Tool definition integrity: Invariant Labs recommends pinning server and tool versions "using hashes or checksums to verify descriptions before use", because of "rug pulls" (definitions changing after approval) — [Invariant Labs, 1 Apr 2025](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks). The MCP Apps spec says hosts should review HTML and "generate hashes or signatures" — [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)

- Opal lets users edit the same workflow conversationally or by drag-and-drop — [InfoQ](https://infoq.com/news/2025/07/google-opal-ai)
- Grey already has: `pipelines.status draft|live` + `current_version`; immutable `pipeline_versions.config` snapshots with note and `published_by`; `eval_sets` → `eval_cases` (question, expected_answer, expected_source_ids[]); and `eval_runs` → `eval_results` (scores jsonb) run on the worker queue (`claim_eval_run`, resume from written results). Eval runs record `pipeline_version` — [grey_current_capabilities.md](C:/Pro/geiger-grey/research_notes/Knowledge%20base%20uses%20beyond%20chat/grey_current_capabilities.md) (`20261010120600_pipelines.sql`, `20261010120800_quality_usage.sql`, `lib/engine/eval_runner.js`)

### Inferences
- Reuse the pipeline pattern: `tools` (draft spec + `status` + `current_version`) and `tool_versions` (immutable spec snapshot, `spec_hash`, note, published_by). Publishing writes a new version. Rollback repoints `current_version`, and nothing is destructive. Published surfaces (REST, widget, MCP) resolve `current_version` unless the key or embed pins a version. The MCP server emits `tools/list_changed` on publish, and the tool `name` or `ui://` URI carries the spec hash so hosts see a new definition instead of a silent change (the rug-pull concern).
- Testing a tool is simpler than testing a chat pipeline because outputs are typed. `tool_test_cases` (an extension of `eval_cases` with `input jsonb`, `expected jsonb`, `assertions jsonb`) can use deterministic assertions: exact label match for classifiers, expected item ids in top-k for similarity search, JSON-schema validity, max latency, max cost. LLM-judged scores are kept only for free-text answers. A classifier test set yields accuracy and a confusion matrix with no judge model, so testing costs the customer less on BYO keys.
- Preview runs should execute the *draft* spec against the real project data through the same interpreter, with a per-step trace (inputs, outputs, tokens, ms, cost) like Dify's variable inspector. Publish should be gated on the test set passing, or on the user explicitly overriding.
- Chat and spec sync: the builder agent should only change the spec through typed edit tools (for example `set_inputs`, `add_step`, `update_step`, `set_labels`, `set_budget`), each validated by Zod against the block catalogue. Each accepted edit creates a draft revision linked to the chat message id. The UI shows a diff, and "undo" is "restore revision N". The conversation is history, not state: when the user edits the spec by hand in a form, the next model turn receives the current spec, so the two can't drift.

- No primary source describes how Opal, Dify's assistant or n8n's builder reconcile chat edits with manual canvas edits (patch-based vs regenerate-whole). This is design inference.

## 5. What are the security risks (prompt injection incl. text hidden in images, tool poisoning, exfiltration via code or URLs) and the recommended mitigations?

### Takeaway
A Grey tool that reads uploaded content holds two legs of Simon Willison's "lethal trifecta": private data and untrusted content. The design must remove the third leg, external communication. The strongest published mitigations are architectural, not filter-based: plan-then-execute, map-reduce with constrained outputs, dual-LLM quarantine, deny-by-default egress, no model-chosen URLs or IDs, and confirmation for consequential actions. Images need specific care, because hidden text can surface only after downscaling.

### Cited Findings
- Lethal trifecta: access to private data, exposure to untrusted content, and the ability to communicate externally. If an agent combines them, "an attacker can easily trick it into accessing your private data" and sending it out. Guardrail products that claim to block "95% of attacks" are not enough, because "in web application security, 95% is a failing grade". Exfiltration vectors include any outbound request: API calls, loading an image, a clickable link — [Simon Willison, 16 Jun 2025](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Design patterns for securing agents (Beurer-Kellner et al., Invariant Labs, IBM, ETH Zurich, EPFL, Google, Microsoft and others, Jun 2025). Central principle: once an agent has ingested untrusted input, "it must be constrained so that it is impossible for that input to trigger any consequential actions". The patterns:
  - **Action-Selector**: map the request to fixed actions, with no feedback from tool output.
  - **Plan-Then-Execute**: fix the actions before reading untrusted data. Injection can still alter arguments.
  - **LLM Map-Reduce**: isolated per-item LLM calls with constrained outputs such as a Boolean or a category, so "a malicious document can only affect its own result".
  - **Dual LLM**: a privileged planner never sees untrusted data, and a quarantined LLM has no tools.
  - **Code-Then-Execute**.
  - **Context-Minimization**.
  - Relevant case studies: resume screening (map-reduce scoring plus dual-LLM summarization), a product recommender (per-review classification into fixed categories), a customer-service bot (a binary topic classifier that could be gamed by mixing questions).
  - [arXiv 2506.08837](https://arxiv.org/abs/2506.08837) ([HTML v3](https://arxiv.org/html/2506.08837v3))
- OWASP LLM01:2025 mitigations: (1) constrain model behaviour; (2) define and *validate output formats with deterministic code*; (3) input and output filtering plus the RAG Triad; (4) least privilege, with the app's own tokens and functions handled in code; (5) human approval for high-risk actions; (6) segregate and identify external content; (7) adversarial testing. Multimodal risk: "hiding instructions in images that accompany benign text". RAG "do[es] not fully mitigate prompt injection", with a scenario where a poisoned repository document skews outputs when retrieved — [OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/). The 2025 list also includes LLM05 Improper Output Handling, LLM06 Excessive Agency, LLM08 Vector and Embedding Weaknesses and LLM10 Unbounded Consumption — [OWASP Top 10 for LLM Apps 2025](https://genai.owasp.org/llm-top-10/)
- Image-scaling injection (Trail of Bits, 21 Aug 2025): prompts invisible at full resolution appear after nearest-neighbour, bilinear or bicubic downscaling. The attack worked against Gemini CLI, Vertex AI, Gemini web, the Gemini API via `llm`, Google Assistant on Android and Genspark. In Gemini CLI it exfiltrated Calendar data through an auto-approving Zapier MCP server. Mitigations: "we recommend not using image downscaling and simply limiting the upload dimensions". "the end user should always be provided with a preview of the input that the model is actually seeing". "text within an image, should not be able to initiate sensitive tool calls without explicit user confirmation". Tool: Anamorpher — [Trail of Bits](https://blog.trailofbits.com/2025/08/21/weaponizing-image-scaling-against-production-ai-systems/)
- Tool poisoning, shadowing and rug pulls: hidden instructions in a tool *description* told the agent to read SSH keys and pass them out in an argument. A malicious tool's description changed how a trusted `send_email` behaved without ever being invoked. Definitions can change after approval. Mitigations: show full descriptions, pin versions by hash, enforce cross-server data-flow boundaries — [Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)
- MCP spec: clients "MUST consider tool annotations to be untrusted unless they come from trusted servers". Servers MUST "Validate all tool inputs", "Implement proper access controls", "Rate limit tool invocations" and "Sanitize tool outputs". Clients SHOULD show tool inputs before calling "to avoid malicious or accidental data exfiltration" — [MCP Tools spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)
- MCP security best practices: SSRF via server-supplied URLs (block private and link-local ranges including `169.254.169.254`, validate redirects, use egress proxies such as Smokescreen, beware DNS-rebinding TOCTOU), token passthrough forbidden, minimal scopes — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)
- Sandbox vendors: a network boundary is needed even with perfect compute isolation ("Without a network boundary, it is only half a sandbox"). Bypasses include an open DNS resolver, fail-open allowlists, parser differentials, and trusted services used as relays — [Vercel blog](https://vercel.com/blog/a-sandbox-without-a-network-boundary-is-only-half-a-sandbox). SNI-only allowlists permit domain fronting — [Vercel firewall docs](https://vercel.com/docs/sandbox/concepts/firewall). Allowing one CDN hostname may permit other destinations on the same endpoint — [E2B internet access](https://docs.e2b.dev/sandbox/internet-access)
- Generated UI exfiltration: MCP Apps defaults to `connect-src 'none'`, and hosts "MUST NOT allow undeclared domains" — [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx). Apps SDK: "Assume prompt injection and malicious inputs will reach your server" and validate even model-produced inputs server-side — [Apps SDK Security](https://developers.openai.com/apps-sdk/guides/security-privacy)
- Code mode privacy: an MCP client can tokenize PII before the model sees it and restore it in downstream calls — [Anthropic Engineering](https://www.anthropic.com/engineering/code-execution-with-mcp)

### Inferences
Threats and mitigations specific to Grey tools:
- **The spec is the plan (Plan-Then-Execute).** The builder agent works only with the user's description and schema, never with uploaded content. At run time the step sequence is fixed. Retrieved chunks, OCR text, image captions and the user's runtime input can change *values*, but not *which steps run* or *what data is in scope*.
- **Constrained generative steps (Map-Reduce / quarantined LLM).** `classify` returns an enum via structured output, and `extract` returns a JSON-schema object validated in code. LLM steps get **no tools**. A poisoned document can then at worst flip its own label or field, which is bounded and testable. Free-text `answer` steps are the residual risk and should carry citations.
- **Remove the exfiltration leg.**
  - Tool runs make no outbound calls except to the project's configured model, embedding and rerank provider endpoints (already fixed in `model_providers`). There is no fetch-URL block in v1.
  - Rendered output must not auto-load model-supplied URLs. Markdown images are disallowed in answers, and links are restricted to Grey's own source links and citation anchors.
  - Thumbnails come from Grey storage by `source_id`, never from URLs the model emits.
- **IDs come from the server, not the model.** A `source_id` or `chunk_id` in output must have come from the search step's actual result set (verified in code). Otherwise a model can't "cite" another project's item, and LLM08 cross-tenant leakage is closed at the interpreter.
- **Images.**
  - Cap upload dimensions instead of silently downscaling, and show the user the exact image the model receives.
  - Treat OCR or VLM-extracted text as untrusted data placed inside clearly delimited fields.
  - Never let image-derived text pick steps or knowledge bases. Image→embedding→vector search is the safest path, because no generative call reads the hidden text.
- **The builder agent's own trifecta.** The builder chat holds the project context and may read sample sources during testing. It should run in Grey's app with tools limited to spec editing and preview runs, and with no ability to publish, create keys or widen KB scope without explicit user confirmation. The AI SDK `toolApproval` mechanism can gate publish.
- **Tool poisoning in reverse.** Grey's MCP server will publish *customer-authored* tool descriptions to external agents. Descriptions should be generated from the spec by a template, length-limited and stripped of instruction-like text, rather than free text written by the builder model, so that a project member can't plant instructions in descriptions that other agents read.

### Gaps
- The Brave research on prompt injection in screenshots, and the OWASP Agentic/MCP Top 10 contents, were not retrieved (search budget). The OWASP site mentions an "Agentic Security" initiative but no list was read.
- No quantitative data on attack success rates against constrained-output (enum) classifiers versus free-text generation.
- No HN or practitioner write-ups on real-world exfiltration incidents through generated widgets were read.

## 6. With bring-your-own models, how can a tool's model cost per run be estimated and capped, and which steps can run with no generative call?

### Takeaway
A declarative spec makes cost *statically boundable*. Each block declares its model calls, and the runtime enforces token ceilings (input truncation plus `maxOutputTokens`). A pre-run estimate is the sum over steps of provider price × max tokens. Grey already records BYOK quantities at cost 0 and has monthly caps with a `retrieval_only` fallback, so per-tool budgets slot in. Embedding, vector search, rerank, graph lookup, deterministic filters and embedding-based classification need no generative call. The precedent for "the person running it pays" is Claude's AI-powered artifacts.

### Cited Findings
- Claude AI-powered artifacts bill usage to the runner: "Their API usage counts against *their* subscription, not yours" — [Claude blog](https://claude.com/blog/claude-powered-artifacts)
- Grey metering: `usage_events.kind` in `page | media_minute | retrieval | llm_tokens | graph_tokens | contextual_tokens | storage_gb`. BYOK kinds are recorded at cost 0 and only Grey's own work (pages, retrievals) is charged. `getCapState` returns `{spend, cap, behavior, reached}`, and cap behaviours are `alert | retrieval_only | pause_ingestion`. New features "can meter without a migration by recording `llm_tokens` with `metadata.purpose`". `ingestion_presets.config` carries a `prices` object. `searchChunks` "already runs without any LLM" — [grey_current_capabilities.md](C:/Pro/geiger-grey/research_notes/Knowledge%20base%20uses%20beyond%20chat/grey_current_capabilities.md) (`lib/engine/usage.js`, `lib/grey/billing.js`, `lib/grey/cost.js`, `lib/engine/turn.js`)
- OWASP LLM10 (Unbounded Consumption) recommends input size limits, rate limits and quotas, timeouts and throttling, limits on queued and total actions, and anomaly monitoring. It names "Denial of Wallet" as the cost-exploitation risk — [OWASP LLM10:2025](https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/)
- AI SDK multi-step loops are opt-in. The default stop condition is `isStepCount(1)`, and per-step `usage` is available in `onStepEnd` — [AI SDK tools](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling)
- Structured Outputs responses can be `incomplete` when `max_output_tokens` is reached, and refusals may not follow the schema, so code must handle both — [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
- Moving data processing into code instead of model context cuts tokens sharply: 150k→2k tokens (98.7%) in Anthropic's example — [Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp). Cloudflare claims 81% on its API — [Cloudflare blog](https://blog.cloudflare.com/dynamic-workers/)
- Map-reduce per-item calls with constrained outputs (Boolean or category) are both a security pattern and a natural per-item cost unit — [arXiv 2506.08837](https://arxiv.org/html/2506.08837v3)

### Inferences
- **No-generative steps (zero LLM tokens; embedding or rerank tokens only):**
  - `embed` (text or image, via the KB's embedding connection), `vector_search` / hybrid search (`searchChunks`), `rerank`, `graph_lookup` (`kg_match_query_entities`/`kg_expand`).
  - `filter` (deterministic predicates on source kind, date, metadata), `threshold`, `top_k`, `dedupe`, `format/template`.
  - **Embedding classification:** either nearest label-description, or k-NN over labelled example items stored in the project. Cost is one embedding call per input. Confidence is the cosine margin, and below a threshold it falls back to "uncertain" or to an LLM step.
  - "Find similar stored items" for an uploaded image is embed → vector search, with no generative call if the KB uses a multimodal embedding model.
- **Generative steps:** `classify(mode: llm)`, `extract`, `answer`, `vision_describe/identify`. Each declares `model`, `maxInputTokens` (enforced by truncating context: top-k chunks × chunk tokens + prompt), and `maxOutputTokens`. For an enum classifier, output is a handful of tokens.
- **Pre-run estimate:** `cost ≤ Σ_steps (maxIn × priceIn + maxOut × priceOut) + embeddingTokens × priceEmbed`. Use the provider price table Grey already keeps (`prices`). Show it in the builder ("≈ $0.0004 per run on your OpenAI key; 1,000 runs ≈ $0.40") and store `estimated_cost` per run.
- **Caps:**
  - A per-tool `budget` in the spec (`maxLLMCalls`, `maxTokensPerRun`, `maxCostPerRun`).
  - Per-key `rate_limit_per_min` (exists) and a per-tool daily run quota.
  - The project monthly cap reused with a `retrieval_only`-style degradation: a tool runs only its non-generative steps and returns "uncertain".
  - Hard runtime timeouts per step and per run.
  - No unbounded loops: agent-style dynamic routing (as in Opal's agent step) stays out of v1, so `stopWhen` is never more than a fixed step count.
- **Metering:** record `llm_tokens` / `retrieval` usage events with `ref_type='tool_run'`, `metadata.purpose='tool'` and `tool_version`, plus a `tool_runs` row (inputs hash, outputs, per-step trace, tokens, latency, cost). This gives customers a per-tool cost view on their own keys and feeds the cost assertions in tests.

### Gaps
- No vendor source was found on per-run *cost estimation UIs* in other builders (Dify, Opal, n8n). Whether any of them pre-compute cost per run is unknown.
- Which of Grey's embedding drivers (openai, cohere, voyage, google, nomic) support image embeddings today was not checked. The visual-search researcher may cover it.

## 7. How can one built tool be published as an internal app, an embeddable widget, a REST endpoint and an MCP tool from one spec?

### Takeaway
All four surfaces can be projections of the same versioned spec. `inputSchema`/`outputSchema` become the REST contract and the MCP tool definition (MCP natively supports `outputSchema` plus `structuredContent`). The same schemas drive the in-app form and result renderer. A single generic MCP Apps resource gives a rich UI in ChatGPT and Claude. Dify already publishes one app as a web app, embed, API and MCP server. Grey has delivery tables (`api_keys`, `widgets`, `mcp_servers.tools`) and a `/retrieve` route skeleton to copy.

### Cited Findings
- Dify publishes one configuration to web apps (auto-generated), website embeds (chat widget or iframe), an API and an MCP server ("Connects the app to tools like Claude Desktop and Cursor"). "Publishing replaces your live app with the current configuration" — [Dify Publish](https://docs.dify.ai/en/cloud/use-dify/publish/README.md)
- MCP tool definitions carry `inputSchema` and optional `outputSchema`, and structured results go in `structuredContent` (plus a serialized TextContent block for backwards compatibility). Errors are reported as `isError: true` with actionable text, and `execution.taskSupport` allows task-augmented (long-running) execution — [MCP Tools spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)
- MCP Apps: a tool links to UI via `_meta.ui.resourceUri`, and `_meta.ui.visibility` can mark helper tools as app-only so they're hidden from the model — [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx). The same UI runs in ChatGPT and other MCP Apps hosts — [OpenAI: MCP Apps in ChatGPT](https://developers.openai.com/apps-sdk/mcp-apps-in-chatgpt/). `registerAppTool()`/`registerAppResource()` emit each host's metadata from one codebase — [Claude docs](https://claude.com/docs/connectors/building/mcp-apps/getting-started)
- Grey delivery today:
  - `POST /api/v1/pipelines/[id]/retrieve` (Bearer key, scope `retrieve`).
  - Keys limited to `ALLOWED_SCOPES = ["retrieve","chat","mcp"]` with `pipelineIds` and rate limits.
  - `mcp_servers` with `tools` jsonb and four read-only tools, and `widgets` with `allowed_domains[]`.
  - New task endpoints "can copy the `/retrieve` route skeleton: `authenticateApiKey`, `resolvePipelineConfig` or a KB boundary, `scheduleDeliveryLog`", but need new key scopes and a new `request_logs.channel` value (check constraints).
  - [grey_current_capabilities.md](C:/Pro/geiger-grey/research_notes/Knowledge%20base%20uses%20beyond%20chat/grey_current_capabilities.md) (`app/api/v1/pipelines/[pipelineId]/retrieve/route.js`, `app/api/api-keys/route.js`)
- Apps SDK: enforce scopes on every tool call and return `401` for expired or malformed tokens, using OAuth 2.1 authorization code (CIMD preferred, else DCR) for external accounts — [Apps SDK Security](https://developers.openai.com/apps-sdk/guides/security-privacy)

### Inferences
- **One spec, four projections:**
  1. **Internal app**: `/p/[project]/tools/[toolId]`, a server-rendered page with a form generated from `inputSchema` and a renderer from `outputSchema` (shadcn and Lucide, matching Geiger Flow and Notes). It runs through a session-authenticated server action.
  2. **REST**: `POST /api/v1/tools/[toolId]/run` (optional `?version=`). It validates the body against `inputSchema`, returns `{ output, version, usage, trace_id }`, and requires a key scope `tools:run` plus a `tool_ids[]` allowlist on `api_keys` (mirroring `pipeline_ids[]`). Long runs (batch classification over many sources) return 202 plus a job id on the worker queue.
  3. **MCP tool**: add the tool to a project MCP server's `tools` jsonb. Name it `tool.<slug>` with the version hash in metadata, `inputSchema`/`outputSchema` from the spec, `annotations.readOnlyHint: true`, `structuredContent` results, and `_meta.ui.resourceUri` pointing at Grey's single generic runner View. Emit `list_changed` on publish.
  4. **Widget**: reuse `widgets` (allowed_domains, theme) with an embed that renders the same form and result components, bound to a widget key scoped to that tool.
- Image inputs differ by surface. REST and the internal app accept multipart or a signed upload URL. MCP accepts an image content item or a resource reference (the spec has image content types). The widget uploads directly to Grey storage under the project path. In every case the interpreter, not the caller, decides where the image is stored and which KBs it is searched against.
- Because surfaces resolve `current_version`, rollback is instant everywhere. Pinning a version per key or embed (a paid feature in Dify) is a cheap differentiator.

### Gaps
- MCP's task-augmented execution (`execution.taskSupport`) semantics for long batch runs were not read in detail.
- How Grey's widget runtime would host non-chat forms (the current widget is chat-only) was not inspected beyond the delivery tables.

## 8. Which design pattern should Grey adopt for the builder and its contained runtime, and why?

### Takeaway
Grey should use a **declarative, versioned ToolSpec interpreted by Grey's own runtime**. It has typed I/O as JSON Schema, a pipeline of whitelisted blocks, a fixed project and KB scope, and a cost budget. A builder agent edits it through typed patch tools. It is tested with deterministic test cases, published as immutable versions, and projected to app, REST, MCP (plus one MCP Apps View) and widget. Arbitrary generated code is deferred to a later opt-in `transform` step, run with no network and no credentials (QuickJS in-process, or Vercel Sandbox `deny-all`). This puts the user's examples (enum classifier; image → similar items / identify / answer) on the cheapest, fastest and most injection-resistant path, and reuses most of Grey's existing tables and engine.

### Cited Findings
- Leading no-code builders use step graphs with fixed classify, extract and retrieve blocks, and keep code as a sandboxed node: Dify (nodes; Code node "blocks file system access, outbound network requests, and system commands"), Opal (step workflow, edited conversationally or by drag-and-drop), n8n (workflow JSON) — [Dify docs index](https://docs.dify.ai/_llms/en/cloud.txt); [Dify Code node](https://docs.dify.ai/en/cloud/use-dify/nodes/code.md); [InfoQ on Opal](https://infoq.com/news/2025/07/google-opal-ai); [Claude: n8n](https://claude.com/customers/n8n)
- Plan-Then-Execute and Map-Reduce with constrained outputs make injection unable to change actions, limiting it to bounded per-item values — [arXiv 2506.08837](https://arxiv.org/html/2506.08837v3)
- Capability stubs with host-held props, plus no ambient network, are the vendor-recommended containment for untrusted code — [Cloudflare bindings](https://developers.cloudflare.com/dynamic-workers/usage/bindings/); [Cloudflare egress](https://developers.cloudflare.com/dynamic-workers/usage/egress-control/). Deny-by-default egress plus credential brokering — [Vercel firewall](https://vercel.com/docs/sandbox/concepts/firewall); [Vercel blog](https://vercel.com/blog/a-sandbox-without-a-network-boundary-is-only-half-a-sandbox)
- MCP Apps is the 2026 standard for tool UI in ChatGPT and Claude — [ext-apps](https://github.com/modelcontextprotocol/ext-apps); [OpenAI](https://developers.openai.com/apps-sdk/mcp-apps-in-chatgpt/); [Claude](https://claude.com/docs/connectors/building/mcp-apps/getting-started)
- Grey already has AI SDK 7, the MCP server SDK 2.x and Zod 4 ([package.json](C:/Pro/geiger-grey/package.json)). It also has pipelines with immutable versions, eval sets and runs on a lease queue, scoped API keys, MCP servers, widgets, usage events and caps, and an LLM-free `searchChunks` — [grey_current_capabilities.md](C:/Pro/geiger-grey/research_notes/Knowledge%20base%20uses%20beyond%20chat/grey_current_capabilities.md)
- Deprecated or ending options to avoid depending on: OpenAI Agent Builder and Evals (end 30 Nov 2026) — [SpotDev](https://www.spotdev.co.uk/blog/agent-builder-wind-down-what-to-do); AI SDK `needsApproval` (deprecated for `toolApproval`) — [AI SDK tools](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling); Vercel Sandbox "runtimes" (deprecated for images) — [Vercel pricing/limits](https://vercel.com/docs/sandbox/pricing); `window.openai`-only widgets (now aliases of MCP Apps) — [OpenAI](https://developers.openai.com/apps-sdk/mcp-apps-in-chatgpt/)

### Inferences
**Recommended architecture ("closed enclosure")**

1. **ToolSpec (data, not code).** Stored as `grey.tools` (draft) and `grey.tool_versions` (immutable snapshot, `spec_hash`), mirroring `pipelines`/`pipeline_versions`. Sketch:
   ```json
   {
     "name": "Defect classifier", "slug": "defect-classifier",
     "scope": { "kbIds": ["…"], "sourceKinds": ["image","document"] },
     "input":  { "type": "object", "properties": { "image": { "type": "string", "format": "grey-image" }, "note": { "type": "string", "maxLength": 2000 } }, "required": ["image"] },
     "steps": [
       { "id": "e",  "block": "embed",         "from": "input.image" },
       { "id": "s",  "block": "vector_search", "query": "e", "topK": 8, "filter": { "kind": "image" } },
       { "id": "c",  "block": "classify",      "mode": "knn", "labels": ["crack","dent","scratch","none"], "neighbors": "s", "minMargin": 0.08,
         "fallback": { "mode": "llm", "model": "provider:model", "maxOutputTokens": 20 } },
       { "id": "a",  "block": "answer",        "context": "s", "question": "input.note", "maxInputTokens": 6000, "maxOutputTokens": 400, "optional": true }
     ],
     "output": { "type": "object", "properties": { "label": { "enum": ["crack","dent","scratch","none","uncertain"] }, "confidence": { "type": "number" }, "similar": { "type": "array" }, "answer": { "type": "string" } } },
     "budget": { "maxLLMCalls": 2, "maxCostPerRunUsd": 0.01, "timeoutMs": 20000 }
   }
   ```
   The block catalogue for v1: `embed` (text/image), `vector_search` (wraps `searchChunks`, with new source-kind and metadata filters), `rerank`, `graph_lookup`, `filter`, `classify` (`knn | label_embedding | llm`), `extract` (LLM plus JSON Schema), `vision_identify` (VLM plus enum/JSON output), `answer` (LLM with citations), `format`. Each block has a Zod schema for its params and a declared cost model.

2. **Builder agent.** An AI SDK 7 agent on the project's BYO model, whose tools are *spec-edit operations* (`set_input`, `add_step`, `update_step`, `remove_step`, `set_labels`, `set_budget`, `run_preview`, `add_test_case`), each validated against the catalogue. It never writes executable code in v1. It is allowed to *read* a small sample of the project's sources to propose labels and examples, but `publish`, scope widening and key creation require explicit user approval (`toolApproval`). Each accepted edit is a draft revision tied to the chat message, so the conversation and the spec can't drift.

3. **Runtime = Grey's interpreter, inside Grey's existing compute.**
   - Interactive runs execute in a Next.js route or server action, and batch runs on the lease-based worker (a new `tool_runs` queue, cloned from `claim_eval_run`).
   - The interpreter builds a **capability context** server-side from the tool version (`projectId`, `kbIds`, provider connections, budget). Blocks can only call engine functions through it, as the Cloudflare `ctx.props` idea implemented in-process. The model never supplies project, KB or source IDs.
   - DB access uses the RLS-scoped path (`can_access_project`) as a second wall.
   - Outbound network goes only to the project's configured model, embedding and rerank endpoints.
   - Per-step and per-run timeouts, token ceilings and budget checks before each generative call apply. Every step writes a trace and `usage_events` (`metadata.purpose='tool'`).

4. **Injection posture.**
   - The spec is a fixed plan.
   - LLM steps are tool-less and output-constrained (enum or JSON Schema validated in code).
   - Citations and similar-item IDs are verified against the actual search result set.
   - No model-emitted URLs are rendered or fetched.
   - Images are dimension-capped, not silently downscaled, with a "what the model sees" preview.
   - OCR/VLM text is treated as untrusted data.
   - Tool descriptions published to MCP are templated from the spec.

5. **Testing and versioning.** `tool_test_cases` (input, expected, assertions) reuse the eval runner shape. Deterministic metrics (accuracy, top-k hit, schema validity, latency, cost) come first, with an LLM judge only for `answer`. Preview runs show a per-step trace. Publish creates an immutable version, rollback repoints `current_version`, and keys and embeds may pin versions.

6. **Publishing.** From one version: an internal page, `POST /api/v1/tools/[id]/run` (new `tools:run` scope plus `tool_ids[]`), an MCP tool on the project server with `outputSchema`/`structuredContent` and a single, hashed, Grey-authored MCP Apps View (`connectDomains` empty), and a widget via `widgets`.

7. **Later phase: a code step.** Add a `transform` block whose body is model-written JavaScript. It runs pure-function style in **QuickJS-in-WASM** inside the worker: no host APIs except the step's input JSON, memory and time limits, and output validated against a schema. Heavier or Python needs go to **Vercel Sandbox** created with `networkPolicy: 'deny-all'`, data passed in as files, and JSON out. That is about $0.0008 per short run on Pro, dominated by the 1-minute memory minimum. Keep it to batch jobs, not interactive runs. Cloudflare Dynamic Workers is the alternative if per-run cost and latency start to dominate. It costs about $0.000001 CPU per 50 ms run plus $0.002 per tool-version per day with stable IDs, but adds a second cloud and runs on V8 isolates rather than a hypervisor.

**Why this pattern for Grey**
- **Safety.** It removes the trifecta's exfiltration leg by construction and applies the two strongest published patterns (Plan-Then-Execute, constrained Map-Reduce). Cross-project leakage would require breaking both the interpreter's capability scoping and RLS.
- **Cost on BYO keys.** Most target tools (similarity search, embedding classification) need zero generative calls, and the rest have statically bounded tokens. Customers see a per-run estimate before publishing, and Grey pays only for its own compute.
- **Latency.** No sandbox boot on the interactive path, and image → embedding → search is a few hundred ms dominated by the provider call. That last figure is an inference and has not been measured.
- **Reliability.** A typed spec can be validated, diffed, tested with deterministic assertions and rolled back. Generated code makes all of these harder.
- **Fit with existing code.** It reuses `pipelines`/`pipeline_versions`, the eval runner and queue, `api_keys`, `mcp_servers`, `widgets`, `usage_events`, caps and `searchChunks`. New pieces are a tools table pair, a block interpreter, image-input plumbing and source-kind/metadata filters for search.
- **Suite consistency.** The UI is generated from schemas using shadcn components rather than model-authored HTML, so tools look native to Geiger Flow and Notes. External hosts get the standard MCP Apps surface.

### Gaps
- Interactive latency for image embedding with each BYO provider, and accuracy of k-NN versus LLM classification on customer data, are unmeasured. A small benchmark on a real project would settle the default `classify` mode.
- Whether to support Opal-style dynamic "agent" steps (runtime routing) at all is an open product decision. It breaks static cost bounds and Plan-Then-Execute, so it is excluded from the v1 recommendation.
- Hacker News and practitioner discussions on sandboxing AI-generated code were not reviewed. The web-search budget was exhausted, and the Algolia HN API was not used as a search substitute because session rules forbid working around the search limit through other search engines.
